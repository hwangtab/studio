# CD·굿즈 판매 페이지(`/shop`) 설계안 — 2026-10-12

상태: **구현됨, 판매는 잠김(`SHOP_SALES_OPEN = false`)** — 2026-10-12. 운영 규칙과 판매 개시 체크리스트는 `lib/shop/CLAUDE.md`가 정본이다. 이 문서는 설계 기록이다.
⚠ 결제수단은 §10이 최신 결정이다(계좌 입금 → 토스 계좌이체). §3·§8·§9의 계좌 입금 서술은 §10이 대체한다.
상품·정책 결정(§2)이 오면 §6 단계대로 착수한다.
근거: 공연 예매(`lib/shows/CLAUDE.md`)·펀딩(`lib/funding/CLAUDE.md`)·계좌 입금(`lib/payments/bankDeposit.ts`)을 읽고 맞췄다.

## 1. 결론

**새 도메인(`merch`)을 공연 예매 방식으로 만든다.** 결제·환불·계좌 입금·메일·관리자는 이미 있는 부품을 쓰고,
새로 쓰는 것은 *상품 정본·재고·배송* 셋이다.

| 후보 | 판정 | 이유 |
|---|---|---|
| 펀딩 리워드로 팔기 | 단발 선판매(예: 사바하 CD 선주문)에만 | 펀딩은 기간·목표금액 모델이라 상시 판매·재고 보충이 안 맞는다. 리워드 id·금액 잠금 규칙도 상시 상품과 충돌 |
| **공연 예매 구조 복제** | **채택** | `orders`(type 추가) + 전용 부속표 + `confirm` 패턴 + 계좌 입금 + 관리자 + 메일이 그대로 대응한다 |
| 외부 스토어(스마트스토어 등) | 제외 | 마켓플레이스 미개설·자사 사이트 집중 방침(메모리 `no-marketplace-site-first`) |

## 2. 먼저 정해 줘야 하는 것 (코드 전에)

기본값을 적어 두었다. 다르면 알려 주면 된다.

1. **상품 분류 — 음반 / 굿즈 두 갈래(운영자 2026-10-12).** 목록 화면은 이 두 분류로 거른다. 올릴 상품은 아직 없다 — 상품 0개일 때 목록·사이트맵·내비가 어떻게 보일지(빈 상태 `EmptyState`, 사이트맵 미등재, 내비 숨김)를 단계 1에서 같이 정한다. 옵션(사이즈·색)·가격·재고는 상품이 정해질 때.
2. **누구의 음반인가** — 스튜디오 발매작인지, 아티스트 위탁 판매인지. 위탁이면 정산이 필요하다(`artist_payouts` 표가 이미 있다). *기본: 스튜디오 직판만.*
3. **배송비 — 4,000원, 20만원 이상 무료(운영자 2026-10-12 확정).** 펀딩은 "배송비 포함 최종가"였지만 상시 판매는 주문 합계에 정액 배송비를 **별도 줄**로 더한다. 판정은 **상품 합계(배송비 제외) ≥ 200,000원이면 0원**. 배송비도 VAT 포함 표기이고 주문 시점 값을 `shop_orders.shipping_fee`에 스냅샷한다. 두 값은 `data/shop` 한 곳(`SHOP_SHIPPING_FEE`·`SHOP_FREE_SHIPPING_FROM`)에서만 읽고, 카피·FAQ·상세의 배송비 문구는 그 상수에서 만든다(가격 리터럴 스캔이 `4,000원`·`20만원`을 잡는다). 상세 화면에 "20만원까지 N원 남음" 같은 안내를 둘지는 화면 단계에서 정한다. 환불로 합계가 20만원 아래로 떨어지는 경우는 1차에 부분 환불이 없어(§8-6) 생기지 않는다 — 부분 환불을 넣을 때 배송비 재계산 규칙을 같이 정한다.
4. **배송 지역** — *기본: 국내만.* 해외 배송은 관세·요금표가 달라 별도 단계.
5. **발송 주체·택배사** — 스튜디오가 직접 포장·발송하는가. 송장번호를 관리자에서 입력하는 흐름으로 짠다.
6. **통신판매업 신고·업태** — 이미 예약·펀딩을 받고 있으니 신고번호는 있을 것이다. 음반·굿즈 소매가 사업자 업태/종목에 걸리는지 세무 확인. CD·굿즈는 **과세**(도서와 달리 면세 아님).
7. **교환·환불 문구** — 법정 7일 청약철회가 기본. CD는 *포장 개봉 시 철회 제한*을 구매 전 화면에 표시해야 제한이 성립한다. 불량·오배송은 판매자 부담.

## 3. 구조 (공연 예매와의 대응)

| 공연(shows) | 상점(shop) | 비고 |
|---|---|---|
| `data/shows/<slug>.ts` 정본 + `seed-show.ts` | `data/shop/<slug>.ts` + `scripts/seed-shop.ts` | 새 상품 = 파일 하나. **금액·SKU id는 오픈 뒤 불변**(펀딩 리워드 규칙과 같다, 가격 변경은 새 SKU) |
| `showtimes` 좌석 | `shop_skus.stock` | 재고는 DB가 정본 |
| `show_orders`·`show_tickets` | `shop_orders`·`shop_order_items` | `orders.orderNo`로 잇는다. 단가·수량·상품명을 **주문 시점 스냅샷**으로 저장 |
| 티켓 QR·입장 | 배송지·`fulfillment_status`·송장 | 배송지는 `shop_orders`에 둔다 |
| `/shows/manage/<orderNo>` | `/shop/manage/<orderNo>` | 주문번호 대문자 → 미들웨어 소문자 308을 **대문자로 정규화해 비교** |

- **`orders.type`에 `'merch'`를 더한다**(`db/schema.ts` `orderTypeEnum`). `orders.status`처럼 DB CHECK가 없어 마이그레이션 없이 들어간다 — 반드시 확인 후 진행.
- **`orders`에 컬럼을 더하지 않는다.** 관계 조회가 전체 컬럼을 SELECT해 배포 순서가 뒤집히면 결제 확인이 깨진다(루트 CLAUDE.md 0022 절). 부속표는 전부 새 표 → 마이그레이션 `0050`+, 미적용 DB에서도 결제는 안 깨진다.
- **재고 점유**: 토스 결제는 `pending` 15분 홀드 후 만료 → 재고 반환. **계좌 입금(`awaiting_deposit`)은 기한 없이 재고를 잡고 자동 취소 없음**(공통 규칙). 재고 집계는 `pending`(홀드 유효)·`awaiting_deposit`·`paid`를 모두 점유로 센다. 차감은 조건부 `UPDATE … WHERE stock >= qty`로 경합을 막는다(`race.integration.test.ts` 같은 시험을 먼저 쓴다).
- **금액**: 상품가는 VAT 포함 표기, `splitInclusiveAmount`로 공급가·VAT 분리 저장(공연과 같다). 서버가 정본에서 합계를 계산하고 클라이언트 금액은 믿지 않는다.
- **결제**: 공용 `usePaymentCheckout`·`PaymentMethodPicker`·계좌 입금 폼 재사용. 토스 승인 채널(위젯/API 키 쌍)은 기존 `confirm*` 규칙 그대로. `bank-deposit:` 키는 토스 환불 경로가 `isBankDepositPayment`로 걸러야 한다.
- **환불**: 발송 전 = 전액 자동(토스 취소 / 계좌는 환불 계좌 접수 후 운영자 송금), 발송 후 = 반품 접수 → 운영자 수동. `refundAccountKindOf`에 `merch` 추가.
- **메일**: 주문 확인(+입금 안내), 발송 안내(송장), 환불. `lib/shows/emailHtml.ts`처럼 순수 HTML 생성 모듈.

## 7. 위험

- **재고 이중 판매** — 토스 홀드 만료·계좌 입금 무기한 점유·동시 결제가 겹친다. 경합 통합 시험이 단계 2의 선행 조건.
- **계좌 입금 장기 점유** — 한정 재고를 입금 안 하는 신청이 오래 잡을 수 있다. 자동 취소는 규칙상 못 하므로 관리자 화면에서 "미입금 취소"를 쉽게 하고 `healthCheck`로 경보.
- **금액 변경 사고** — 오픈 뒤 SKU 가격을 파일에서 바꾸면 기록과 어긋난다. 펀딩 기준선 게이트(`content/funding.baseline`)와 같은 `shop` 기준선 테스트를 같이 만든다.
- **세무** — 매출 구분(음반/굿즈)·현금영수증/세금계산서 요청 대응은 §2-6 확인 뒤 정한다.

## 8. 설계 점검에서 찾은 빈틈 (2026-10-12)

코드를 다시 열어 확인한 것만 적는다. 위 §3~§5에 없던 것이라 단계 2의 선행 조건이다.

1. *(§10으로 해소 — 상점은 계좌 입금을 쓰지 않아 환불 계좌를 받지 않는다. 사실 기록으로 남김)* **`refund_accounts.order_kind`에는 DB CHECK가 있다**(`'funding','session','mixing','show'`, 마이그레이션 0048). §3에서 "`refundAccountKindOf`에 `merch`만 더하면 된다"고 했지만 틀렸다 — CHECK 때문에 `merch` 행이 INSERT에서 거부된다. SQLite는 CHECK를 ALTER로 못 바꾸므로 **표 재생성 마이그레이션**이 필요하다(데이터 복사 후 교체). 배포보다 먼저 적용, 환불 계좌 접수만 실패하는 종류의 순서 의존이다. 대안: 상점 환불 계좌를 별도 표로 두기(표 재생성 회피) — 결정 필요.
2. **토스 웹훅이 `orders.type`으로 분기하고 모르는 type은 `'session'`으로 떨어진다**(`lib/booking/webhook.ts` 승인 복구·취소 대사 두 곳, `order?.type ?? 'session'`). `merch` 분기를 안 넣으면 상점 주문이 **예약 확정 경로**로 가서 조용히 실패하거나 엉뚱하게 처리된다. 승인 복구(`confirmMerchOrder`)와 취소 대사(`syncMerchCancelsFromToss`) 분기를 둘 다 추가하고, 알 수 없는 type이 예약으로 새지 않게 하는 시험을 쓴다.
3. **주문번호 접두어**: 예약 `SNB`, 펀딩 `FND`, 티켓 `TKT`. 상점은 `SHP-YYYYMMDD-XXXXXXXX`로 하고 `lib/payments/recordFailure.ts`의 주문번호 패턴 허용 목록에 추가해야 결제 실패 사유가 기록된다(안 하면 조용히 안 남는다). 접두어는 소문자 308을 견디게 대문자 hex 그대로 두고 비교는 대문자 정규화.
4. *(§10으로 해소 — 상점에 입금 대기 주문이 없다)* **계좌 입금 쪽 목록 2곳**: `lib/payments/bankDepositOrders.ts`의 `BANK_DEPOSIT_ORDER_TYPES`(같은 이름 이중 입금 후보)와 `pages/admin/bookings/index.tsx`의 입금 대기 조회는 type을 하드코딩한다. 상점 입금 대기를 넣지 않으면 **다른 종류 신청과의 이중 입금 확인 방지가 상점만 빠진다**. 상점 전용 관리자 목록을 만들더라도 앞의 후보 조회에는 `merch`를 포함한다.
5. **크론 3종**: 토스 홀드 만료(`expire-show-orders` 같은 `expire-shop-orders`, 재고 반환), 주문 개인정보 파기(`purge-orders` — 상점 배송지는 `orders`가 아니라 `shop_orders`에 있어 **기존 파기 경로에 안 걸린다**; 펀딩이 `retention.ts`를 따로 둔 이유와 같다), 발송 지연 경보(`health-check`). `vercel.json` 크론 등록 포함. 파기를 빠뜨리면 배송지·전화번호가 무기한 남는다.
6. **재고 복원 규칙**: 환불·미입금 취소·홀드 만료 때 재고를 돌려주는 곳이 최소 4곳이다. 같은 주문이 두 경로에서 동시에 복원되면 재고가 부풀므로 **복원은 주문 상태 전이(CAS)와 같은 batch에서 한 번만** 한다. 부분 환불(일부 품목 반품)은 1차에서 하지 않고 전액만 — 펀딩의 `lineRefund`처럼 줄 단위 환불은 2차.
7. **배송비 환불 규칙**: 단순 변심 반품은 고객이 왕복 배송비를 부담하는 것이 일반적이고 불량·오배송은 판매자 부담이다. 발송 전 전액 취소는 배송비 포함 전액 환불. 이 세 경우를 `refundPolicy`처럼 순수 함수 한 곳에 두고 화면·FAQ·서버가 같이 쓴다(공연 `refundPolicy.ts` 방식).
8. **상품 정본과 DB 사본의 관계가 문서에 없었다.** 공연처럼 "파일이 정본, DB는 사본"이면 재고 수량을 파일에서 바꾸면 안 된다(DB 재고를 덮어씀). 규칙: 파일에는 SKU id·이름·가격·옵션만, **재고는 시드가 최초 1회만 넣고 이후는 관리자만** 바꾼다. 시드 재실행이 재고를 리셋하지 않는 시험 필수.
9. **개인정보 수집 최소화**: 배송지는 필수지만 CD만 사는 경우도 우편 발송이라 필요하다. 주민번호·생년월일은 받지 않는다. 배송 메모는 선택. 휴대폰 번호는 택배사에 위탁 제공되므로 처리방침의 위탁 항목에 택배사명을 적는다(§5와 연결).
10. **디지털 음원 번들 여부 결정이 없다.** CD에 다운로드 코드를 끼우면 `funding/download.ts` 같은 내려받기 경로와 청약철회 예외(디지털 콘텐츠)가 따라온다. 1차는 **실물만**, 코드 번들은 제외로 못 박는다.
11. **테스트 지도**: `*.integration.test.ts`는 공연·펀딩마다 있다(`race`·`confirm`·`refund`·`bankDeposit`·`seed`). 상점도 같은 5종 + 웹훅 분기 시험 + 기준선(SKU id × 단가) 시험을 단계 2의 완료 기준으로 둔다. `npx jest`는 디렉터리를 좁히지 않는다(디자인 가드가 `tailwind.config.test.ts`에 있다).

### 수정된 §6 단계 2 선행 목록

마이그레이션(표 3~4개 + `refund_accounts` CHECK 처리) → 웹훅 분기 → 주문번호 패턴 → 입금 후보 목록 → 크론 3종 → 경합·복원 시험. 이 순서 전에는 결제를 열지 않는다.

## 9. 결제 편의 점검 — 펀딩·공연과 같은 수준인가 (2026-10-12)

코드로 확인한 결과 **카드·간편결제는 그대로 같은 수준이 된다.** 계좌 입금은 부품은 다 있지만 **펀딩과 공연이 정반대 규칙**을 쓰고 있어 상점이 어느 쪽을 따를지 정해야 한다.

### 9-1. 그대로 쓰면 같은 수준이 되는 것

| 편의 | 쓰는 부품 | 상점에서 할 일 |
|---|---|---|
| 카드·카카오페이·네이버페이·토스페이·페이코·애플페이 | `usePaymentCheckout`(위젯 기본 / `?pay=v2` 목록) — 네 폼 공용 | 훅을 부르기만 하면 된다. 플래그·쿠키·애플페이 판정이 자동으로 따라온다 |
| 결제창을 닫아도 같은 버튼으로 재시도 | 공연 폼의 `pendingRef`(같은 입력이면 만든 주문 재사용, 홀드 만료 1분 전까지) | 복제. 안 하면 재시도마다 재고 홀드가 하나씩 쌓인다 |
| 위젯 준비 지연 없음 | 공연 폼의 `IntersectionObserver` 선로딩 | 복제 |
| 회원가입 없음 | `orders.manage_token` 비밀 주소(`/shop/manage/<orderNo>`) | 공연과 같다 |
| 동의 체크박스 없음 | "결제하기를 누르는 행위로 동의" | 같다. 청약철회 제한(CD 개봉)·배송비 문구만 버튼 위에 |
| 승인 키 쌍 | success 주소의 `tosskey=api` → `confirm*(channel)` | **상점 success 페이지가 `channel`을 넘겨야 한다** — 빠뜨리면 목록 모드 결제가 승인에서 키 불일치로 한 번 더 돈다(재시도는 되지만 느림) |
| 결제 실패 사유 기록 | `recordFailure` | §8-3 주문번호 패턴 추가가 전제 |
| 애플페이 iframe 권한·토스 CSP | `middleware.ts` 전역 정책 | 경로별이 아니라 할 일 없음 |

### 9-2. 펀딩에만 있고 공연에는 없는 것 — 상점에 꼭 필요하다

- **주소 검색** — `components/funding/kakaoPostcode.ts`(카카오 우편번호, 키 없음, CSP 이미 허용). 펀딩 폴더에 있으므로 `components/common/`(또는 `payments/`)으로 옮겨 공용으로 쓴다. 공연은 배송이 없어 이게 없다 — **공연 폼만 복제하면 주소 검색이 빠진다.**
- **입력 초안 저장** — `lib/formDraft.ts`(PledgeWizard·BookingWizard). 이름·연락처·주소만 저장하고 **수량·선택은 저장하지 않는다**(재고가 바뀌므로 — 펀딩의 규칙). 인앱 브라우저에서 결제창이 튕겨 돌아와도 주소를 다시 안 친다.
- **여러 상품 한 번에** — 펀딩의 "함께 받기"(같은 화면에서 다른 리워드 수량 추가). 상점은 별도 장바구니 페이지 대신 **상세 화면에서 다른 상품도 담는 방식**을 1차로 한다. 배송비 4,000원이 주문당 한 번이라 "같이 사면 배송비 한 번"이 바로 보이는 것이 편의의 핵심이다. 장바구니(페이지 간 유지)는 2차.

### 9-3. 계좌 입금 — 규칙이 둘이다. 하나를 골라야 한다 *(§10으로 대체)*

| | 펀딩 | 공연 |
|---|---|---|
| 한정 수량에 계좌 입금 | **막는다**(`bankTransferBlockReason` → "카드·간편결제로만") | **받는다** |
| 재고·좌석 | 무제한 리워드만이라 잡을 것이 없다 | 기한 없이 잡는다(`hold_expires_at` NULL) |
| 이유 | 확인까지 며칠 걸리는 사이 다른 사람이 품절을 보거나, 확인하는 순간 이미 다 팔림 | 좌석 이중 판매를 막고, 노년층 은행·ATM 입금을 받기 위해 |

상점은 **전 상품이 한정 재고**라 펀딩 규칙을 그대로 쓰면 계좌 입금이 **아예 사라진다.**

**권장: 공연 방식(재고를 잡고 받는다).** 계좌 입금을 되살린 이유가 은행·ATM에서 보내는 노년층 고객이었고(2026-10-04), CD 구매층과 겹친다. 대신:

1. **확정(운영자 2026-10-12): 한정 재고도 계좌 입금을 받는다. 재고 소량 차단 기준은 두지 않는다.** 펀딩의 `bankTransferBlockReason`을 상점에 가져오지 말 것 — 가져오면 전 상품에서 계좌 입금이 사라진다. 품절 직전 상품이 미입금 신청에 묶이는 위험은 아래 2번(관리자 미입금 취소 + 경보)으로만 관리한다.
2. 자동 취소는 없다(공통 규칙). 대신 관리자 상세에 **신청 후 경과일**을 크게 보이고 "미입금 취소"를 한 번에. `healthCheck`에 3일 넘은 입금 대기 경보.
3. 공연에는 있는 "회차 시작 2시간 전 차단"(`bankDepositBlockReason`)은 상점에 해당 없음(`startsAt: null`).

### 9-4. 계좌 입금 흐름 — 그대로 쓸 수 있는 것과 새로 할 것 *(§10으로 대체)*

- 신청 → 바로 `/shop/manage/<orderNo>`로 문서 이동 → **`BankDepositGuide`**(계좌·금액 가장 크게, 복사 버튼, 기한 지나도 계좌 유지, 카운트다운 없음). 공용이라 그대로 쓴다. `applicantLabel="주문하신 분"`.
- 입금 안내 메일(고객+운영자)·주소당 시간당 3통 제한(`depositGuideThrottle`)·관리자 재발송 — `deliverShowDepositGuide` 구조 복제.
- 입금 전 고객 취소 / 관리자 미입금 취소 → `deposit_cancelled` + **같은 batch에서 재고 반환**(§8-6).
- 입금 확인 → `bank-deposit:<주문번호>` 결제 행 → 주문 확인 메일. 재고는 이미 잡혀 있어 재검증이 필요 없다(공연과 같고, 펀딩이 한정 리워드를 막은 이유가 여기서 해소된다).
- 입금 후 환불 → `RefundAccountFields`(공용)로 고객이 환불 계좌 입력 → 운영자 송금 → "송금 완료". `refund_accounts` CHECK 문제는 §8-1.
- **현금영수증 — 확정(운영자 2026-10-12): 운영자가 홈택스에서 수동 발급하고, 상점 화면·메일·FAQ에는 언급하지 않는다.** 신청 칸도 두지 않는다. 그래서 코드에 현금영수증 관련 칸·문구를 만들지 않는다. 음반·굿즈 소매가 의무발행 업종인지(의무면 고객 요청이 없어도 발급해야 한다)는 세무 확인으로 남긴다(§2-6) — 의무 업종이면 이 결정을 다시 본다.

### 9-5. 결론

- 카드·간편결제: **공연과 같은 수준**(공용 훅 그대로). 다만 공연 폼만 베끼면 **주소 검색·초안 저장이 빠진다** → 펀딩에서 가져온다.
- 계좌 입금: 화면·메일·환불 부품은 전부 공용으로 있다. 한정 재고도 받고(공연 방식), 현금영수증은 수동 발급·화면 언급 없음으로 확정됐다.

## 10. 결정 변경 — 계좌 입금 대신 토스 계좌이체 (운영자 2026-10-12)

**상점은 "계좌로 직접 입금"(무통장)을 쓰지 않고 토스 계좌이체(`method: 'TRANSFER'`)를 쓴다. 공연 예매도 같은 방향으로 바꾼다.**
이유(운영자): 직접 입금은 환불이 생기면 고객 환불 계좌를 받아 손으로 송금해야 해 너무 번거롭다. 토스 계좌이체는 토스 취소 API 한 번으로 원래 계좌에 돌아간다.

이 결정은 2026-10-04 결정 둘을 상점·공연에서 뒤집는다 — 알고 뒤집는 것으로 기록한다.
- "토스 계좌이체는 넣지 않는다"(`lib/payments/paymentChoices.ts` 주석) — 이유는 **PC에서 은행 보안 프로그램 설치 화면이 떠 결제가 막힌다**였다. 그 문제는 그대로 있다.
- "계좌 입금 재도입 — 은행·ATM에서 보내는 노년층"(#475) — 토스 계좌이체는 인터넷뱅킹 인증이라 ATM 입금자는 쓸 수 없다. 이 층은 카드·간편결제로 가거나 카카오 문의로 온다.

### 10-1. 상점에서 사라지는 것 (설계가 단순해진다)

`awaiting_deposit` 상태, 무기한 재고 점유, 입금 안내 메일·스로틀, 관리자 입금 확인·미입금 취소, `BankDepositGuide`, 환불 계좌 표(§8-1), 입금 후보 목록(§8-4), 입금 대기 경보. 재고 점유는 **토스 홀드(`pending` 15분) 하나**만 남고, 만료 크론이 반환한다. 환불은 전부 토스 취소다.

### 10-2. 새로 확인·처리할 것

1. **토스 콘솔에 계좌이체가 개통돼 있는가**(MID studkol3wd, 위젯 키 쌍·API 키 쌍 둘 다). 안 돼 있으면 계약 추가부터. 수수료는 카드와 다르다(계좌이체는 건당 정률+최저 수수료 구조) — 콘솔 계약 화면에서 확인.
2. **두 결제 화면 모두에서 나와야 한다.**
   - 위젯(기본값): 위젯은 콘솔에 개통된 수단을 그대로 그린다. 개통하면 **펀딩·예약·믹싱 위젯에도 함께 뜬다** — 상점·공연만 열 수 없다. 위젯에서 수단을 화면별로 고르려면 위젯 결제 UI(variantKey)를 화면마다 나눠야 한다(콘솔 설정). 이 범위를 먼저 정한다.
   - 결제수단 목록(`?pay=v2`): `PAYMENT_CHOICES`에 `transfer`(라벨 "계좌이체")를 더하고 `buildTossPaymentRequest`에서 `method: 'TRANSFER'`로 연다. 화면별로 목록을 거르는 인자를 둔다(상점·공연에만 보이게, 직접 입금은 상점·공연에서 숨김).
   - 키 쌍 규칙은 그대로다 — 판정은 브라우저에서 결제창을 실제로 열어 한다(2026-09-15 교훈: API 응답만 보면 "된다"로 잘못 읽는다).
3. **부분 취소가 되는가.** 공연 환불은 매수 단위 부분 취소(취소환불표 비율)다. 토스 계좌이체 부분 취소 지원 여부·은행 점검 시간대 취소 지연을 문서와 실결제로 확인. 안 되면 공연은 부분 환불이 막힌다. 상점 1차는 전액 취소뿐이라 영향이 작다.
4. **승인 응답의 `method: '계좌이체'`**는 `KNOWN_PAYMENT_METHODS`에 이미 있어 알림이 뜨지 않는다. 처리방침 1항이 계좌이체 응답에 실리는 항목(은행·정산 상태 등)을 설명하는지 확인 — `POLICY_DESCRIBED_METHODS`에 없는데 응답에 개인정보가 실리면 처리방침 개정(→ `FUNDING_TERMS_VERSION`)이 필요하다.
5. **현금영수증**: 토스 계좌이체는 결제창이 현금영수증 신청을 받아 토스가 발급한다. "수동 발급·화면 언급 없음" 결정(§9-4)은 상점에서는 사실상 토스 결제창이 대신하게 된다 — 우리 화면에는 여전히 쓰지 않는다.
6. **PC 보안 프로그램 문제를 화면에서 어떻게 다룰지** — 막혔을 때 고객이 카드·간편결제로 돌아올 수 있게 실패 페이지(`/shop/fail`·`/shows/fail`)의 문구를 "다른 결제수단으로 다시 시도"로 둔다. 토스가 돌려주는 실패 코드는 `recordFailure`가 남긴다.

### 10-3. 공연 예매 전환 (별도 PR)

- `ShowBookingForm`의 결제수단에서 "계좌로 직접 입금"을 빼고 토스 계좌이체를 넣는다. **서버의 계좌 입금 경로(`lib/shows/bankDeposit.ts`·관리자 입금 확인·환불 계좌)는 지우지 않는다** — 이미 들어온 `awaiting_deposit` 주문과 입금 뒤 환불이 남아 있을 수 있다. 운영 DB에서 공연 `awaiting_deposit`·`refund_accounts(order_kind='show')` 미송금 건을 먼저 센다. 0건이면 신규 생성만 막고, 나머지 코드는 다음 정리 때 걷는다.
- 서버 `createShowOrder`도 `paymentMethod: 'bank_transfer'`를 거절하게 한다(화면만 숨기면 API로는 계속 들어온다).
- `lib/shows/CLAUDE.md`의 "계좌 입금" 절, `lib/shows/faq.ts`(FAQ 답이 실제 동작에서 만들어진다), 루트 CLAUDE.md "계좌 입금은 펀딩·공연·예약·믹싱 공통" 절, `paymentChoices.ts` 주석을 같은 PR에서 고친다.
- 펀딩·예약·믹싱의 직접 입금은 **이번 결정 범위 밖**이라 그대로 둔다(바꾸려면 따로 결정).

## 11. 구현과 달라진 점 (2026-10-12)

- **재고를 차감하지 않고 계산한다**(§3의 "조건부 UPDATE … WHERE stock >= qty" 대신). `shop_skus.stock`은 총수량, 남은 수량은 점유 주문을
  빼서 매번 계산 — §8-6(재고 이중 복원)이 구조적으로 사라졌다. 이중 판매는 생성 게이트 + 확정 게이트(나를 뺀 재판정)로 막는다.
- 부속표는 셋(`shop_skus`·`shop_orders`·`shop_order_items`, 마이그레이션 0052). 환불 계좌 표 문제(§8-1)는 직접 입금이 없어 해당 없음.
- 만료 정리는 새 크론 대신 공연 만료 크론에 붙였다(크론 수를 늘리지 않으려고, 실패는 갈라 둠).
- 처리방침 개정·메뉴·사이트맵은 **판매를 열 때** 한다(체크리스트). 상품이 없는 지금 배송지를 받을 일이 없다.
