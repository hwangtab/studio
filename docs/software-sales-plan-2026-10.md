## 1. 결론

**1차는 국내 원화 판매, 토스페이먼츠의 페이팔 계약이 열리면 같은 결제 연동으로 해외(USD)를 연다. 라이선스의 정본은 우리 DB다.**

- **국내(KRW)** — 상점(`merch`)과 같은 구조로 새 주문 종류 `software`를 만든다. 토스 결제·승인·웹훅·환불·메일·관리자는 있는 부품을 쓴다.
- **해외(USD)** — 토스페이먼츠가 페이팔을 해외간편결제로 제공한다(`FOREIGN_EASY_PAY` · provider `PAYPAL` · currency `USD`).
  별도 페이팔 계정 연동 없이 **같은 토스 연동에 결제수단 하나를 더하는 일**이라, 국내 판매 코드를 그대로 쓰고 통화만 갈라진다.
  정산도 토스 대시보드 하나로 모인다.
- 새로 만드는 것은 **상품 정본 · 라이선스(발급·활성화·검증) · 설치 파일 전달**, 그리고 해외 단계의 **통화(USD)** 처리다.

| 후보 | 판정 | 이유 |
|---|---|---|
| **토스(국내) → 토스 페이팔(해외)** | **채택** | 결제 연동 하나, 장부 하나. 계약 심사 중(2026-10-14) |
| Merchant of Record(Paddle·Lemon Squeezy) | 예비안 | 해외 VAT를 대신 신고해 주는 대신 수수료 약 5%+, 라이선스·장부가 둘로 갈린다. §5의 VAT 부담이 감당 안 되면 이리로 돌린다 |
| iLok/PACE 복제 방지 | 제외 | 연 $5,000 수준(2차 출처). AAX 서명만 PACE EDEN으로 해결한다(§6) |

## 3. 구조

### 3-1. 상품 정본 — 파일 하나

`data/software/<slug>.ts` 한 파일이 상품이다(공연·상점과 같은 방식).
담는 것: 이름·설명(ko/en), **가격 `{ krw, usd }`**, 포맷·OS·최소 사양, 체험 기간, 최대 기기 수, **릴리스 목록**(버전·날짜·변경 내역·OS별 설치 파일 R2 키·sha256).
**상품 id·가격은 오픈 뒤 불변**(펀딩 리워드 규칙과 같다). 가격 변경은 새 가격 id. 기준선 테스트로 고정한다(`data/shop/catalog.baseline.json` 방식).
가격은 `data/pricing.test.ts` 리터럴 스캔에 걸리므로 카피는 상수에서 끌어온다(`formatPriceLabel`).

### 3-2. DB (마이그레이션 1개, 새 표만)

| 표 | 칸 | 비고 |
|---|---|---|
| `orders` | `type = 'software'` 추가 | `orderTypeEnum`만 늘린다(DB 제약 없음). 주문번호 접두사 `SWR-` |
| `software_orders` | order_no, **currency(`KRW`/`USD`)**, **amount_minor**(USD는 센트), buyer_country, product_id·price_id 스냅샷, refund_waiver_agreed_at | 통화를 `orders`에 칸으로 더하지 않는다 — 관계 조회가 전체 칸을 SELECT해 마이그레이션 전 배포 시 결제 확인 전체가 깨진다(0022 사례). 별도 표면 그 위험이 없다 |
| `software_licenses` | id, product_id, license_key(평문 — 구매자 화면에서 다시 보여 줘야 한다. 새어도 기기 수 한도가 피해를 묶는다), email, order_no, max_activations, status(active/revoked/refunded), issued_at, first_activated_at | 한 주문에 상품이 여럿이면 라이선스도 여럿 |
| `software_activations` | license_id, machine_hash, label, activated_at, deactivated_at | 동시 활성 수 = `deactivated_at IS NULL` 개수 |

새 표뿐이라 순서를 어겨도 다른 결제는 안 깨진다(상점 0052와 같다). 적용은 그래도 배포보다 먼저.
`first_activated_at`이 펀딩의 `downloaded_at` 역할을 한다 — 청약철회 판정의 근거(§4).

**해외 단계 전에 바뀌는 것:** `orders.totalAmount`·`itemAmount`·`vatAmount`는 지금 원화 정수 전제다. USD 주문은
`software_orders.currency/amount_minor`가 정본이고, `orders` 금액 칸에 무엇을 둘지(원화 환산? 0?)는 매출장부·세무 신고 방식과 함께
단계 3 착수 때 정한다. `splitInclusiveAmount`(10% VAT 분리)를 USD 주문에 그대로 쓰지 않는다 — 해외 공급의 부가세는 §5 답에 따른다.

### 3-3. 라이선스 방식 — 온라인 활성화 1회 + 오프라인 서명 파일

1. 결제가 확정되면 서버가 라이선스 키를 만들어 메일·확인 페이지로 준다.
2. 플러그인에 키를 넣으면 `/api/software/activate`가 기기 수를 확인하고 **기기에 묶인 서명 파일**을 돌려준다.
3. 플러그인은 내장 공개키로 그 파일을 검증한다. 이후는 **오프라인으로 동작**한다(스튜디오 컴퓨터는 인터넷을 끄는 일이 많다).
4. 인터넷이 없는 기기용으로 확인 페이지에서 서명 파일을 직접 내려받는 길도 둔다(Valhalla DSP 방식).

- 형식은 **Ed25519 서명 JSON 하나**다. JUCE 내장 `OnlineUnlockStatus`(RSA)를 쓰지 않는 이유: 상품이 JUCE와 비JUCE로 섞여 있어 형식이 둘이 되면 서버·테스트가 두 벌이 된다.
  Ed25519 검증은 C++(Monocypher 단일 파일)·Python·JS 모두 몇 줄이다 — `docs/software/license-integration.md`.
- 서명 비밀키는 Vercel env(Sensitive)에만 두고, 잃으면 기존 라이선스 검증이 다 깨지므로 **오프라인 백업**을 둔다
  (`FUNDING_FIELD_KEY`와 같은 취급, `lib/crypto/CLAUDE.md` 참고). 공개키는 플러그인에 박히므로 **키 회전 = 플러그인 재배포**다. 처음부터 키 id를 서명 파일에 넣어 두 키를 동시에 받을 수 있게 한다.
- 활성화 API는 IP·라이선스별 레이트리밋(`consumeRateLimit`), 키 추측 방지(실패 응답 동일·지연).
- 복제 방지는 "정직한 사람을 정직하게 두는" 수준까지만.

### 3-4. 설치 파일 전달

- **체험판(공개)**: 누구나 받는다. 파일명에 버전을 박는다(같은 경로에 새 파일을 덮지 않는다 — immutable 캐시).
  체험판과 정식판은 **같은 설치 파일**이다. 라이선스가 들어오면 정식으로 바뀐다.
- **구매자 화면**: `/[locale]/software/manage/<orderNo>?token=<manageToken>` — 라이선스 키, 활성 기기 목록·해제, 오프라인 서명 파일, 버전별 설치 파일.
  펀딩 다운로드와 같은 패턴(POST 시작 · `isTokenMatch` · R2 10분 presign · 302). 큰 설치 파일도 R2 직접 전달이라 함수 4.5MB 한도와 무관하다.
- **잃어버린 링크 재발송**: 지금 사이트에 없는 기능이다. 이메일을 넣으면 그 주소로 구매 내역 링크를 다시 보낸다
  (존재 여부를 응답으로 드러내지 않는다 — 항상 "보냈습니다"). 라이선스는 몇 년 뒤에도 찾아오는 상품이라 이게 없으면 문의가 쌓인다.
- 업데이트 알림: 플러그인이 `/api/software/latest?product=`를 하루 한 번 묻는다(개인정보 없이). 새 버전이 나와도 메일을 돌리지 않는다 — 광고성 정보 판단을 피한다.

### 3-6. 해외 결제 — 토스 페이팔 (단계 3)

토스 계약이 열리면 같은 폼에 통화 갈래를 더한다.

- **통화 선택**: 로케일이 아니라 **구매자 선택**이다 — en 화면 기본 USD(PayPal), ko 화면 기본 KRW. 한국 사는 외국인·해외 사는 한국인이 다 있다.
- **SDK 호출**: `amount: { currency: 'USD', value: 49.00 }`, `method: 'FOREIGN_EASY_PAY'`, `foreignEasyPay: { provider: 'PAYPAL', country }`.
  결제위젯을 쓰면 **같은 통화의 결제수단끼리 하나의 variantKey로 묶어야** 한다(토스 문서). 공용 `usePaymentCheckout`에 통화 인자를 더하는 일이고,
  가드(`sharedCheckout.guard`)가 막는 "공용 체크아웃 밖 SDK 직접 호출"은 하지 않는다.
- **토스 키 쌍**: 페이팔이 어느 키 쌍(위젯 `gck` / API `ck`)에 개통되는지 계약 뒤 브라우저에서 실제로 불러 확인한다
  (루트 CLAUDE.md "토스 키는 두 쌍이다" — API로만 확인하면 "된다"는 잘못된 결론이 나온다).
- **승인·환불**: 금액 대조를 통화 포함으로 바꾼다(`value`+`currency`가 서버 정본과 같아야 승인). USD 부분환불은 소수점 금액이다.
  페이팔 분쟁(chargeback)은 토스 대시보드로 온다 — 분쟁 들어온 라이선스는 운영자가 관리자에서 `revoked`로 돌린다.
- **영어 화면**: 토스 결제위젯 iframe은 한국어 고정이다(공연 en에서 확인). 페이팔 창은 페이팔이 그린다. 우리 화면·메일만 영어(`lib/shows/emailEn.ts` 본보기).
- **고쳐야 할 기존 사실 가드**: `lib/factGuards.ts`의 `foreign-payment-method-claim`(PayPal "받지 않는다", 2026-07-28 확인) —
  개통일에 규칙을 "PayPal은 소프트웨어 해외 결제에서만"으로 바꾼다. 처리방침에 해외 결제(토스 위탁 범위·국외 이전 여부)를 고지하고 `FUNDING_TERMS_VERSION`을 올린다.

| 처리방침 | 수집 항목(이름·이메일·기기 식별값 해시), 목적(라이선스 발급·활성화·재발송), 보유기간(라이선스 유지 기간), 위탁(토스·Cloudflare R2). ko 변경이므로 `FUNDING_TERMS_VERSION` 올리고 기준선 갱신 | 할 일 |
| 업태·종목 | 소프트웨어 판매가 사업자 업종에 걸리는지 | 세무사 확인 |

## 5. 해외 판매 세무 (단계 3 전) — ⚠ 결제가 열려도 세금은 따로 남는다

토스 페이팔은 **결제 대행이지 판매 대행(MoR)이 아니다.** 판매자는 그대로 스튜디오 놀이고, 해외 소비자 대상 디지털 판매의 현지 세금 의무도 우리에게 남는다.

| 지역 | 의무(2차 출처) | 선택지 |
|---|---|---|
| EU | 비EU 사업자의 소비자 대상 디지털 서비스는 **첫 1유로부터** VAT 등록(Non-Union OSS — 한 회원국에 등록해 EU 전체를 분기 신고) | 등록하고 판다 / 등록 전까지 EU 판매 막음 |
| 영국 | 면세점 없음, 20% | 등록하고 판다 / 막음 |
| 그 밖(미국·호주·일본 등) | 대체로 매출 면세점이 있어 초기 소량 판매는 해당이 적을 것으로 보이나 국가별 확인 필요 | 세무사 확인 |
| 한국 부가세 | 해외 판매분 영세율 여부 — 외화 수취 요건(국세청은 PayPal 원화 수취 건을 영세율에서 제외한 사례가 있다). 토스 정산이 원화인지 외화인지가 갈림길 | 세무사 확인 + 토스에 정산 통화 문의 |

**기본안**: 해외 판매를 열 때 구매자 국가를 받아(결제 전 선택 + 페이팔 응답의 국가로 대조) EU·영국은 "준비 중"으로 막고 시작한다.
판매가 붙으면 OSS·영국 등록을 하든지, 그 시점에 해외분만 MoR로 돌린다. 막는 국가 목록은 상품 정본 옆 한 곳(`data/software/policy.ts`)에 둔다.

**세무사에게 물을 것(한 번에)**: ① 해외 B2C 소프트웨어 다운로드 판매의 국내 부가세(영세율·외화 수취 요건, 토스 정산 통화 기준) ② EU OSS·영국 VAT를 1인 사업자가 직접 할 때의 부담과 대행 비용 ③ 소프트웨어 판매 업종 추가 필요 여부.

## 7. 단계

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| 0. 결정·서류 | §2 남은 결정 4개, 세무사 질의(§5 세 문항), Apple·Windows 서명 준비, AAX 신청 | 결정 확정, 서명 인증서 손에 있음 |
| 1. 라이선스 코어 + 체험판 | 상품 정본, 표 2개(라이선스·활성화, 마이그레이션 1개 — 주문 표는 단계 2), 관리자 수동 발급, 활성화·검증·최신버전 API, 서명 키 백업, 상품 화면(ko/en, 체험판 다운로드), 플러그인 쪽 검증 연동 | 관리자 수동 발급 키로 실제 DAW에서 활성화 → 오프라인 동작 → 기기 해제 → 다른 기기 활성화. **판매는 잠금**(`SOFTWARE_SALES_OPEN=false`, 상점과 같은 방식) |
| 2. 국내 판매 | §3-5 배선, 구매자 manage 화면, 링크 재발송, 메일, 관리자, 약관·처리방침 개정(§4) | 최소 금액 실결제 → 키 수령 → 활성화 전 환불 → 키 거절, 그리고 활성화 후 셀프 환불이 막히는지까지 한 바퀴. 카드·간편결제·계좌이체 각 1건 |
| 3. 해외 판매 | 토스 페이팔 개통 확인(키 쌍), 통화 갈래(§3-2·§3-6), 국가 제한(§5), 영어 메일, factGuards·처리방침 수정 | USD 실결제 → 라이선스 → 부분·전액 환불까지. 매출장부에 통화가 맞게 찍힘. 세무사 답 반영 |
| 4. 이후 | 메이저 업그레이드 가격, 번들, 교육용 할인, (AI 툴이 서버형이면) 구독·크레딧, EU·영국 개방 | 판매 데이터 보고 결정 |

단계 1을 판매와 떼어 둔 이유: 라이선스 검증이 플러그인 바이너리에 들어가는 순간 형식을 바꾸기 어렵다. 결제를 붙이기 전에
실제 DAW에서 활성화·오프라인·기기 해제를 먼저 굳힌다. 단계 1은 토스 심사와 무관하게 지금 시작할 수 있다.

## 8. 하지 않는 것

- 무통장 입금 — 즉시 발급이 안 된다.
- 환율 연동 가격 — 원화가·달러가를 따로 고정한다.
- 복제 방지 강화(iLok, 상시 온라인 확인) — 사용자 불편이 판매 손실보다 크다.
- 회원 가입·로그인 — 주문번호 + 토큰 + 이메일 재발송으로 간다. 상품이 여럿 쌓여 필요해지면 다시 본다.
- 체험판과 정식판의 설치 파일 분리.
- 새 버전 안내 메일 — 플러그인 안 알림으로 대신한다.

## 9. 외부 사실의 확인 상태

공식 확인: 토스페이먼츠 페이팔 제공·별도 페이팔 계정 불필요·자동 정산(토스 블로그), USD·JPY 다통화 결제와 USD 소수점 지원(토스 문서), JUCE `OnlineUnlockStatus`(무료).
2차 출처만: `FOREIGN_EASY_PAY`/`PAYPAL` 호출 형태와 위젯 variantKey 통화 묶음(토스 개발자 커뮤니티), EU·영국 VAT 면세점 없음, PACE 비용, Apple·Windows 인증서 가격, AAX 서명 무료 배정.
미확인(계약·문의로 확인): 토스 페이팔 **수수료·정산 통화·디지털 상품 허용 여부**, 개통되는 키 쌍, 전자상거래법 제17조 해당 호 번호, 해외 B2C 판매의 영세율.
