# 음원 제작 용역 전자계약 — 설계 검토 (2026-10-18)

대상 문서: `음원제작용역계약서_20261018.pdf`(싱글 1곡, 1,150,000원, 13개 조).
참조: 연습실 전자계약(`lib/contracts/`, `pages/[locale]/contracts/`, `pages/admin/contracts/`, 마이그레이션 0046까지).
설계는 `docs/production-contract-design-2026-10.md`.

## 1. 결론

- **서명 엔진은 연습실 것을 재사용하고, 계약 레코드는 따로 둔다.** `contracts` 표는 호실·월세·보증금·이용 기간이
  `NOT NULL`이고 호실 충돌 검사·`subscriptions`·이용수칙 첨부·해지(terminated) 의미가 전부 연습실 전제다. 제작 계약을
  거기 끼우면 빈 값과 예외 분기가 곳곳에 생긴다. 새 표만 추가하면 기존 조회에 영향이 없어 **배포 순서 함정(0022·0035류)도 없다.**
- **서명보다 서명 뒤가 이 계약의 본체다.** 연습실 계약은 서명하면 대부분 끝나지만, 제작 계약은 조항 절반이 날짜에 기대어
  집행된다(7일 간주 승인, 14일 연체, 30일 무응답, 4주 지연, 8주 작업 기간과 그 연장). 그 날짜를 증명할 기록이 없으면
  조항이 있어도 분쟁 때 쓸 수 없다. 그래서 2단계로 **진행 기록(이벤트 원장)**을 둔다.
- 첫 계약 종류는 `production-single`이고, EP·정규도 같은 엔진에 템플릿만 더해 올리도록 만든다.

## 2. 조항별로 시스템이 떠받쳐야 하는 것

| 조항 | 계약서 내용 | 시스템에 필요한 것 |
|---|---|---|
| 제2조 | 범위(편곡 10트랙·녹음 3시간 등), 인도물 WAV·MP3 | 계약 조건 값(트랙 수·녹음 시간)을 계약별로 굳혀 보관 |
| 제3조 | 계약금 575,000원(체결 후 3일), 잔금 575,000원(최종 승인 후 7일, 인도 전) | 입금 확인 기록(일시·금액), 기한 계산, 잔금 전 인도 잠금 |
| 제4조 | 작업 기간 = 계약금 입금 **그리고** 1차 완성본 수령일부터 약 8주, 의뢰인 사유 지연은 제외 | 기산일 = 두 날짜 중 늦은 쪽. 정지 구간(사유 포함) 기록 → 남은 기간 계산 |
| 제5조 | 무료 수정 편곡 2·믹싱 2·마스터링 1회, 초과 회당 10만·5만·3만원. **전달 후 7일 내 요청 없으면 승인 간주** | 단계별 결과물 전달 일시, 수정 요청 회차, 명시/간주 승인 구분, 초과 수정 청구 |
| 제6조 | 세션 실비·추가 녹음은 사전 동의 후 | 추가 비용 동의 기록(누가·언제·얼마) |
| 제7조 | 크레딧 `Arranged by 황경하 / Recorded · Mixed by 스튜디오 놀` | 계약별 크레딧 문자열 보관(유통 등록 때 대조) |
| 제10조 | 착수 정의, 착수 전 전액 환불, 착수 후 항목표 기준 공제 | 착수 시각 기록, 항목별 완료 상태 → 환불액 계산 |
| 제10조 5항 | 30일 무응답·14일 연체 시 통지 후 해지 | 마지막 연락 시각, 연체 일수, **해지 통지 발송 기록** |
| 제12조 2항 | 스튜디오 사유로 4주 이상 지연 시 의뢰인 해지 가능 | 지연이 누구 사유인지 기록(정지 구간 사유와 같은 자료) |
| 제13조 | 양 당사자 전자서명 시 성립, 미성년자는 법정대리인 공동 서명 | **다자 서명**(운영자·의뢰인·법정대리인) |

7일 간주 승인은 특히 "언제 전달했는가"를 스튜디오가 증명해야 성립한다. 카톡으로 파일을 보내고 끝나면 그 증명은 대화방
캡처에 기댄다. 전달을 시스템에서 하고(메일 + 의뢰인 진행 페이지), 전달 시각과 메일 발송 결과를 남기면 연습실 계약의
열람 기록(`firstViewedAt`)과 같은 역할을 한다.

## 3. 연습실 시스템에서 가져올 것 / 못 쓰는 것

**그대로 쓴다(순수 모듈·인프라)**

- 본인 확인: `identity.ts`(연락처 뒷자리, 화면 마스킹)
- 서명 이미지 검증: `signature-validation.ts`
- 표 셀 이스케이프·치환: `html-escape.ts`의 `escapeTableCell`, 치환값을 함수로 넘기는 방식(`$'` 주입 방지)
- KST 날짜·금액 표기: `format.ts`
- 접속 IP·열람 기록: `client-ip.ts`, `view-log.ts`
- 관리자 인증·세션·요청 제한: `admin-auth.ts`·`admin-session.ts`·`admin-rate-limit.ts`·`admin-accounts.ts`
- PDF: `pdf.ts`(Chromium 렌더, 외부 요청 차단), `pdf-storage.ts`(Blob), 직인 `CONTRACT_SEAL_BASE64`
- 메일 발송·실패 기록 패턴(`notificationError`), 3년 파기 크론·백업 크론 패턴
- 개인정보 접근 기록(`privacy` 로그의 `contract_view`·`contract_pdf_download`)

**설계 원칙을 그대로 옮긴다**

- 템플릿 사본(0046): 계약 생성 때 템플릿 원문을 떠 두고 서명 때 그 사본으로 본문을 완성한다.
- 조건부 batch(`sign-transaction.ts`): 모든 쓰기를 "아직 서명 대기 + 이 토큰 + 미만료"에 건다.
- 버전 접두사가 붙은 지문(`integrity.ts`의 `v4:` 방식): 새 엔진은 `p1:`부터 시작한다.
- 계약일은 서명 순간의 KST 날짜로 확정한다(PDF의 "2026년 10월 18일" 고정 인쇄는 템플릿 변수로 바꾼다).

**못 쓴다(연습실 전용)**

- `contracts` 표 자체, `REQUIRED_CLAUSES`(보증금·금지행위 등), 이용수칙 첨부, 호실 충돌, `subscriptions` 연결
- `validation.ts`의 **만 19세 미만 차단** — 제작 계약은 법정대리인 공동 서명을 허용한다(4장 b 참조)
- 서명 화면(`sign.tsx`, 837줄): 서명 캔버스가 페이지 안에 직접 짜여 있다. `SignaturePad` 컴포넌트로 먼저 뽑아낸 뒤
  두 화면이 같이 쓴다. 연습실 화면은 동작이 그대로인지만 확인한다.

## 4. 시스템을 만들기 전에 계약서에서 정할 것

시스템이 계약서 문구를 그대로 집행하므로, 문구가 모호하면 코드도 모호해진다. 법률 판단이 걸린 항목은 자문을 받을 것.

a. **운영자 전자서명이 실제로 없다.** 제13조는 "양 당사자가 전자서명한 때 성립"이라고 하고 서명란에 "대표 황경하
   (전자서명)"이 있다. 연습실 시스템은 운영자 서명 행위를 기록하지 않고 PDF에 직인 이미지만 찍는다. 제작 계약은
   **발송 버튼 = 운영자 서명**으로 만든다(관리자 계정·시각·IP를 서명 행으로 남기고 지문에 포함). 운영자가 먼저 서명하고
   의뢰인(및 법정대리인)이 마지막에 서명한 순간이 성립 시각이 된다.

b. **미성년자 공동 서명의 본인 확인이 약하다.** 법정대리인에게 별도 링크와 별도 연락처 뒷자리 확인을 걸어도 "이 사람이
   실제 부모인가"는 확인하지 못한다. 대리인 동의가 없던 것으로 드러나면 미성년자는 계약을 취소할 수 있다. 선택지:
   ① 1단계는 연습실처럼 만 19세 미만을 막고 오프라인으로 처리, ② 대리인 서명 + 운영자가 가족관계 증빙을 확인하고
   확인 사실을 기록. 미성년 의뢰인이 드물면 ①로 시작하는 쪽이 안전하다.

c. **개인정보 조항이 없다.** 실명·생년월일·주소·연락처(대리인 포함)를 받는데 수집 목적·보유 기간이 계약서에 없다.
   연습실 계약은 제12조에 이것을 두고 파기 크론이 그 약속을 지킨다. 제작 계약도 보유 기간을 정해야 파기 크론을 붙일 수 있다.
   (대금·계약 기록에 다른 법정 보존 기간이 걸리는지는 확인 필요.)

d. **관할 조항이 연습실 계약과 다르다.** 제작 계약은 "서울서부지방법원 합의 관할", 연습실 계약은 "민사소송법에 따른다" +
   1372·소비자원 안내다. 같은 서식을 반복해 쓰면 약관으로 볼 수 있고, 개인 의뢰인에게 불리한 관할 합의는 약관규제법상
   다툼의 여지가 있다. 연습실 쪽이 의도적으로 고른 문구라면 맞추는 것을 검토할 것.

e. **"진행 중인 항목은 진행 정도에 따라 비율로"(제10조 3항)는 계산할 수 없다.** 시스템은 완료/미완료만 확실히 안다.
   단계 경계를 정해 두면 환불액을 시스템이 그대로 낸다. **편곡은 1차 시안을 전달하면 100%(완료)로 본다 — 운영자 결정
   2026-10-18.** 계약서 제10조 3항에 이 문장을 넣어야 집행할 수 있다.

f. **금액은 계약마다 굳힌다.** 1,150,000원 = 소편성 편곡(`ARRANGEMENT_SMALL_PRICE` 50만) + 싱글 번들(`SINGLE_BUNDLE_PRICE`
   50만) + 보컬 보정(`VOCAL_TUNING_ADDON_PRICE` 15만)으로 정본 상수와 맞는다. 작성 폼은 이 상수로 미리 채우되 저장값은
   계약별로 둔다(상수가 바뀌어도 서명된 계약은 그대로). 환불 항목표 합계 = 계약금액, 계약금 + 잔금 = 계약금액을 검증한다.
   초과 수정 요금(10만·5만·3만)은 `data/pricing.ts`에 없다 — 사이트에도 쓸 값이면 상수로 올린다.

g. **크레딧 문구는 변수로.** 편곡자가 바뀌는 계약(외부 편곡가)이 생기면 템플릿을 고치지 않고 값만 바꾼다.

## 5. 데이터 모델 (새 표 4개, 기존 표 무변경)

```
service_contracts            계약 1건
  id, kind('production-single'), status(draft|sent|signed|cancelled|expired|completed|terminated)
  title, client_name, client_stage_name, client_email, client_phone, client_birthdate, client_address
  terms_json                 계약 종류별 조건(금액·분할·환불표·수정 횟수·초과 요금·녹음 시간·트랙 수·크레딧·작업 주수)
  content                    완성된 본문(서명 때 확정)
  content_hash               'p1:<sha256>' — 본문·terms_json·서명자 전원을 덮는다
  sent_at, signed_at, expires_at, completed_at, terminated_at, termination_reason, purged_at
  notification_error, created_at, updated_at

service_contract_templates   생성 시점 템플릿 사본 (0046과 같은 역할)

service_contract_signers     서명자별 행 — operator / client / guardian
  role, name, email, phone, relation(대리인 관계), sign_token, expires_at
  identity_verified_at, first_viewed_at, view_count, signed_at, ip, user_agent, signature_data

service_contract_events      진행 기록 — 추가만 하고 고치지 않는다(정정은 새 이벤트)
  type, stage(arrangement|recording|tuning|mixing|mastering), round, amount, occurred_at,
  actor(admin 계정|client), note, notice_sent_at, notice_error
```

`terms_json`은 계약 종류마다 스키마를 코드에 두고(`lib/serviceContracts/kinds/productionSingle.ts`) 생성·서명·PDF가
같은 스키마로 읽는다. EP·정규는 kind 하나와 템플릿 하나를 더하면 된다. 컬럼으로 펼치지 않는 이유는 계약 종류가 늘 때마다
마이그레이션이 생기기 때문이다. 검색·정렬이 필요한 값(의뢰인·상태·금액 합계)만 컬럼으로 둔다.

이벤트 종류(초안): `deposit_received`, `source_received`(1차 완성본), `kickoff`(착수), `stage_delivered`,
`revision_requested`, `stage_approved`(explicit|deemed), `pause_started`/`pause_ended`(사유: client|studio),
`extra_cost_agreed`, `balance_received`, `final_delivered`, `distribution_submitted`, `released`, `termination_notice`.
남은 작업 기간·수정 잔여 횟수·간주 승인 예정일·현재 기준 환불액은 이 원장에서 계산한다(저장하지 않는다).

## 6. 흐름

1. **작성** — 관리자 화면에서 kind 선택 → 정본 상수로 채워진 조건 확인·수정 → 미리보기.
   (3단계: 견적 요청서 `lib/quote/estimate.ts` 결과에서 바로 초안 만들기.)
2. **발송 = 운영자 서명** — 운영자 서명 행 확정, 의뢰인 링크 메일 발송(7일 만료, 재발송 시 토큰 회전).
3. **의뢰인 서명** — 열람 기록 → 연락처 뒷자리 확인 → 생년월일·주소·활동명 입력 → 필수 동의 조항 체크
   (제5조 수정·간주 승인, 제7조 권리 귀속·크레딧, 제10조 환불, 개인정보) → 서명.
   미성년자를 받는다면 여기서 대리인 링크가 나가고, 대리인 서명까지 끝나야 `signed`.
4. **성립 후처리** — 지문 계산, PDF 생성·보관, 의뢰인·운영자 메일(연습실 `finalize.ts`와 같은 구조).
   계약금 안내(계좌·기한)를 같은 메일에 싣는다.
5. **진행** — 관리자가 이벤트를 남기면 의뢰인에게 메일이 가고, 의뢰인은 진행 페이지에서 현재 단계·남은 수정 횟수·
   승인 기한을 본다. "승인" 버튼을 누르면 명시 승인 이벤트가 남는다.
6. **기한 크론**(매일) — 간주 승인 전날 안내, 7일 경과 시 `stage_approved(deemed)` 기록과 통지, 계약금·잔금 기한 경과 알림
   (운영자에게 먼저), 4주 지연 위험 경고(운영자에게). 해지 통지는 자동으로 보내지 않는다 — 운영자가 버튼으로 보내고 그 발송이
   제10조 5항의 "서면 통지" 기록이 된다.

## 7. 단계별 범위

| 단계 | 내용 | 끝나면 되는 것 |

## 8. 운영자가 정할 것

1. 미성년 의뢰인: 1단계에서 막을지(권장), 대리인 서명을 바로 열지 (4-b)
2. 개인정보 보유 기간과 조항 문구 (4-c)
3. 관할 조항을 연습실과 맞출지 (4-d)
4. "진행 중 항목" 환불 비율의 단계 경계 (4-e) — 편곡은 결정됨(1차 시안 전달 = 100%), 나머지 항목 남음
5. 결과물 전달을 시스템으로 할지(권장) — 파일은 기존처럼 드라이브 링크로 두고, 전달 사실과 시각만 시스템이 남기는 방식도 된다
