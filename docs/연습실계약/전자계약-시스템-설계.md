# 전자계약 시스템 설계 (2026-07-27)

음악연습실 이용계약을 온라인 서명으로 체결하는 시스템. 2026-07-23 프로토타입(E2E 동작 확인)을
운영 가능한 상태로 완성하는 작업의 설계 문서.

## 1. 상태 머신

```
draft ──발송──▶ sent ──서명──▶ signed
  │              │ ▲
  │취소          │ │재발송(토큰·만료 갱신)
  ▼              ▼ │
cancelled      expired (발송 후 7일 경과, lazy 판정)
```

| 상태 | 의미 | 가능한 전이 |
|---|---|---|
| `draft` | 작성됨, 고객에게 미발송 | → sent(발송), → cancelled(취소), 삭제 가능 |
| `sent` | 발송됨, 서명 대기 | → signed(서명), → expired(만료), → cancelled(취소), 재발송 |
| `signed` | 서명 완료 | 종착 상태. 삭제 불가(법적 보존) |
| `expired` | 서명 링크 만료 | → sent(재발송) |
| `cancelled` | 운영자가 취소 | → sent(재발송) |

**만료는 크론 없이 lazy 판정한다.** 서명 페이지·서명 API·관리자 목록 조회 시 `expiresAt`을
검사하고, 지났으면 그 시점에 `expired`로 전환한다. Vercel Cron을 추가하지 않는 이유는 계약 건수가
적고(월 수 건) 만료 판정이 필요한 시점이 곧 접근 시점이기 때문이다.

**재발송은 signToken을 재생성한다.** 기존 링크는 즉시 무효화되며 `expiresAt`이 7일 뒤로 갱신된다.

## 2. 스키마 변경

`sentAt` 컬럼 1개만 추가한다(`expiresAt - 7일`로 역산 가능하지만 발송 이력은 명시 기록이 필요).
나머지는 기존 컬럼(`expiresAt`, `agreedAt`, `signTokenUsedAt`)을 활용한다.

### 마이그레이션 이력 재베이스라인

현재 이력이 깨져 있다 — 저널에 `0002_lovely_switch`가 있으나 SQL 파일이 없고, `schema.ts`의
`sign_token_used_at`은 어느 스냅샷에도 없다. 실제 Turso 스키마만 `schema.ts`와 일치한다.

프로덕션 배포 전이고 DB가 하나뿐이므로 **이력을 baseline 하나로 리셋**한다:

1. `schema.ts`에 `sentAt` 추가
2. 실 DB에 `ALTER TABLE contracts ADD COLUMN sent_at integer`
3. `drizzle/migrations/` 삭제 후 재생성 → 전체 CREATE TABLE 하나
4. Turso `__drizzle_migrations` 초기화 후 baseline 해시(= SQL 파일 내용의 sha256) 삽입

이후 `db:generate`/`db:migrate`가 정상 동작한다.

## 3. API

| 라우트 | 메서드 | 변경 |
|---|---|---|
| `/api/contracts` | POST | `draft`로 생성. 이메일 발송하지 않음 |
| `/api/contracts` | GET | 만료 lazy 판정 후 목록 반환 |
| `/api/contracts/[id]` | GET | 관리자 응답에 `signUrl` 포함 (링크 복사 버그 수리) |
| `/api/contracts/[id]` | PATCH | **신규** — `action: send \| resend \| cancel \| update` |
| `/api/contracts/[id]` | DELETE | **신규** — `draft`/`cancelled`만 삭제 |
| `/api/contracts/[id]/sign` | POST | 동의 항목 서버 검증 + `agreedAt` 기록, 만료 검사 추가 |
| `/api/admin/auth` | POST | 로그인 rate limit 추가 |
| `/api/db/test` | — | **삭제** (스키마 노출) |

`update`는 `draft` 상태에서만 허용하며 계약 본문을 재생성한다. 발송 후에는 수정 대신
취소 → 새 계약 생성으로 유도한다(서명 대상 문서의 무결성).

## 4. 관리자 UI

- **`/admin/contracts/new`** (신규) — 생성 폼. 저장하면 `draft` 상태로 상세 페이지 이동
- **상세 페이지** — 상태별 액션: draft `[발송][수정][삭제]`, sent `[링크 복사][재발송][취소]`,
  signed `[PDF]`, expired/cancelled `[재발송]`
- **동의 항목 표시 수리** — 현재 무조건 "✓ 동의"로 표시하나, 실제 `agreedAt` 유무로 판정
- 목록 상단에 로그아웃 버튼

## 5. 서명 페이지 수리

- **canvas 좌표 스케일 버그** — 내부 해상도(720×200)와 CSS 표시 크기가 달라 모바일에서 서명이
  어긋난다. `rect.width` 대비 비율로 보정
- 체크한 동의 항목 id를 서버로 전송(현재는 클라이언트에서만 검사)
- **개인정보 수집·이용 동의(제12조)** 를 필수 동의 항목에 추가
- 만료·취소된 링크 접근 시 안내 화면

## 6. 배포 대응 (Vercel)

프로토타입이 로컬에서만 동작하는 구조라 다음을 전환한다:

- **PDF 생성** — `puppeteer` → `puppeteer-core` + `@sparticuz/chromium`. 로컬에서는 설치된
  Chrome을 자동 탐색한다. 서버리스 번들 크기·실행 가능성 문제 해소
- **응답 후 작업 유실 방지** — 서명 API가 응답을 보낸 뒤 PDF 생성·이메일 발송을 계속하는데,
  서버리스에서는 응답 즉시 실행이 중단될 수 있다. `@vercel/functions`의 `waitUntil()`로 감싼다
- **런타임 파일 트레이싱** — `template.ts`가 계약서 템플릿과 이용수칙 마크다운을
  `readFileSync`로 읽는다. 경로가 동적이라 Next.js 파일 트레이싱이 감지하지 못해 배포 시
  `ENOENT`가 난다. `next.config.mjs`의 `outputFileTracingIncludes`에 명시한다.
  이용수칙 원본은 트레이싱이 닿는 `lib/contracts/house-rules.md`로 옮겼다
- **PDF의 한글 폰트** — 서버리스 Chromium에는 한글 폰트가 없어 그대로 두면 계약서 전체가
  두부(□)로 인쇄된다. 완성형 11,172자를 담은 `pretendard-variable-full.woff2`를 base64로
  인라인한다(본문용 subset은 KS X 1001 기반이라 드문 음절의 이름이 깨질 수 있어 쓰지 않는다)

## 8. 테스트

`lib/contracts/` 순수 함수에 단위 테스트를 추가한다 — 상태 전이 규칙, 페이로드 검증,
서명 데이터 검증, 템플릿 치환. DB·puppeteer에 의존하는 부분은 테스트하지 않는다.

## 9. 운영자 날인

계약서 서명란의 `<span class="seal">`이 비어 있어 갑의 날인 없이 발행되고 있었다.
`public/images/contract-seal.png`를 단일 원본으로 삼아 PDF는 base64 인라인
(`buildSealCss`), 화면은 URL 참조(`components/contracts/ContractContent.tsx`)로 채운다.

마크다운 렌더러가 이 `span`을 지우면 날인이 조용히 사라지므로 회귀 테스트로 고정한다.

## 10. 백업과 복구

Turso가 유일본이라 DB를 잃으면 어떤 계약이 있었는지조차 알 수 없다. 서명 완료 건은 PDF가
Blob과 고객 메일에 남지만, 작성 중·서명 대기 계약은 흔적도 남지 않는다.

주 1회 크론(`/api/cron/backup-contracts`)이 계약·서명·조항·첨부를 통째로 JSON으로 떠서
Blob(`contracts/backup/`)에 보관한다. 보관 기간은 28일 — 복구는 대개 사고 직후에 필요하고,
백업에는 이름·연락처가 그대로 들어 있어 오래 두면 제12조로 약속한 파기가 사본에서
무의미해진다. 같은 작업에서 어느 계약도 가리키지 않는 PDF도 정리한다(업로드 24시간 유예).

백업이 조용히 실패하면 "백업이 없다"는 사실을 사고가 난 뒤에 알게 되므로, 실패는 운영자
메일로 알린다.

### 복구 절차

1. Blob에서 가장 최근 백업을 읽는다. private이라 URL 직접 접근은 403이고,
   `get(url, { access: 'private' })`로 받아야 한다.
2. `contracts` → `signatures` → `contract_clauses` → `contract_attachments` 순으로 넣는다
   (외래키 순서).
3. **`sent` 상태 계약은 모두 재발송한다.** 백업에는 서명 토큰이 없다(유출 시 링크가 통째로
   딸려 나가는 것을 막기 위해 뺐다). 재발송하면 새 토큰이 발급되고 기존 링크는 무효가 된다.
4. `signed` 계약의 PDF는 Blob에 그대로 있다. `pdfUrl`이 가리키는 파일이 지워졌다면
   관리자 화면의 PDF 다운로드로 계약 내용에서 다시 만들 수 있다.

## 범위 밖

- 계약 갱신 자동화, 결제 연동, 알림톡 — 별도 과제
- 이용자(을) 서명은 계약서 본문 표가 아니라 전용 전자서명 블록에 이미지·서명 시각·IP와 함께
  기록한다. 본문 표의 "(서명)" 표기는 원본 서식을 그대로 둔다
