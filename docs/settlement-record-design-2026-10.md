# 상점·공연 주최자 정산 기록 설계 (2026-10-16)

> 상태: **P1(상점 월 정산 + 보존·파기 코드 확장) 구현 완료 — 마이그레이션 0067, 2026-10-16.** P3(정산 안내 메일·정산 CSV) 구현 완료 — 2026-10-16(마이그레이션 없음). P2(공연)는 별도. (아래는 원 설계 그대로.) 운영자 확정: 정산 기록 보관·파기 규칙은 상점·공연 개설자에게도 적용(7절). 나머지 열린 질문(9절)에는 권장 답을 적어 두었다. 정산할 일이 생기기 전까지 만들지 않아도 된다.
> 원칙 한 줄: **시스템은 계산하고 기록한다. 송금은 운영자가 은행 앱으로 하고, 끝났다고 기록한다.** 은행 이체 연동은 만들지 않는다.

## 1. 지금 있는 것 / 없는 것

| | 펀딩 | 아티스트 후원 | 상점 | 공연 주최자 |
|---|---|---|---|---|
| 정산 계산 | `lib/funding/payout.ts` | `lib/artistSupport/payout.ts` | `lib/shop/artistPayout.ts`(예정 표) | **없음** |
| 정산 기록(스냅샷) | `funding_project_payouts` | `artist_payouts` | **없음** | **없음** |
| 지급 완료 기록 | ○ | ○ | **없음** | **없음** |
| 계좌·세금 정보 | 개설자 콘솔 정산 탭(암호화, 열람 기록) — 상점·공연도 같은 계정(`funding_creators`)을 쓴다 ||||
| 약관상 규칙 | 개설자 약관 제6조 | — | 위탁 약관 제7조 | 주최자 약관 제6·7조 |

상점은 `/admin/shop`의 "아티스트 정산 예정" 표가 그 달(KST)에 **발송한** 결제 완료 주문을 세어 보여 주고, 운영자가 손으로 이체한다. 이미 정산한 달의 반품 환불은 자동으로 빠지지 않아 손으로 뺀다.
공연은 계산 자체가 없다 — 주최자 현황 링크는 "정산 금액이 아니라 참고용"이라고 적혀 있다.

## 2. 정산 단위 (결정안)

- **상점: 아티스트 × 달(KST).** 약관 제7조가 "정산한 뒤에 환불된 판매는 다음 정산에서 뺀다"고 이미 정해 두었다 — 달 단위 + 이월 조정이 계약과 맞는다. 시기는 약관상 "스튜디오가 따로 알린다"(권장: 매월 10일까지 전월분, 코드로 강제하지 않는다).
- **공연: 공연 1건 × 1회.** 주최자 약관 제6조: "마지막 회차가 끝난 날부터 영업일 14일 이내"에 판매액에서 환불을 먼저 빼고 수수료를 떼어 정산. 회차별 정산은 하지 않는다(환불·회차 취소가 서로 섞이므로).
- 정산 대상자: DB 개설자(`funding_creators`)가 기본. 상점의 파일 갈래 아티스트(`file:<slug>`, 큐레이션 몇 명)는 계좌 정보가 시스템에 없어 **기록·지급 완료는 되지만 계좌 열람 버튼은 없다**(운영자가 따로 안다).
- 스튜디오 자신의 상점 계정(`STUDIO_SHOP_ARTIST_SLUG`)과 스튜디오 직영 공연(`data/shows/*.ts`, 주최자 없음)은 정산 대상이 아니다.

## 3. 계산 규칙 (새로 정하는 것은 거의 없다)

**상점** — 기존 `computeShopArtistPayout` 그대로: 판매가(VAT 포함) − 환불 → 55% + (아티스트 직접 발송 주문) 배송비 100% → 개인은 부가세 상당액(10/110)과 원천징수 3.3% 공제, 사업자는 공제 없음(세금계산서). 철회 가능한 디지털 주문은 "철회 가능 N건"으로 띄우고 **정산에서 빼 둔다**(기간이 지나면 다음 정산에 들어간다).

**공연** — 펀딩과 같은 요율(상수 `FUNDING_PLATFORM_FEE_PERCENT` 5.5% + `FUNDING_PAYMENT_FEE_PERCENT` 3.3%, 약관이 같은 상수를 보간한다):
```
판매액   = 결제 확정된 티켓의 단가 합 (초대권·0원 제외)
순판매액 = 판매액 − 완료된 환불
수수료   = round(순판매액×5.5%) + round(순판매액×3.3%)
정산 기준 = 순판매액 − 수수료 − 회차 취소 결제수수료 부담분(아래)
개인(원천징수) / 사업자 처리 = 펀딩과 동일 (computeBusinessIncomeWithholding 재사용)
```
- **회차 취소**: 그 회차 결제분은 전액 환불되지만 토스 결제 수수료는 돌려받지 못한다. 약관 제7조대로 스튜디오 귀책이 아니면 주최자가 그 3.3%를 부담 → **조정 행**으로 정산금에서 뺀다. 귀책 여부는 운영자가 회차 취소 때/기록 때 체크(기본값: 주최자 부담).
- 정산금이 모자라면 **차액(shortfall)**을 기록에 남기고 협의·청구(펀딩의 `shortfall_amount`와 같은 개념). 실지급액은 음수가 되지 않는다.

## 4. 데이터 모델 (마이그레이션 1개, 표 2개)

`partner_payouts` — 펀딩 정산 기록(`funding_project_payouts`)과 같은 모양을 상점·공연이 같이 쓴다.
```
id, kind('shop'|'show'), subject_key, period,            -- unique(kind, subject_key, period)
  -- shop: subject_key = 'creator:<id>' | 'file:<slug>', period = 'YYYY-MM'
  -- show: subject_key = show id,                         period = 'all'
creator_id (nullable), payee_name (스냅샷), tax_type (스냅샷),
gross_amount, refund_amount, shipping_amount,
platform_fee_amount, payment_fee_amount, studio_amount,   -- 상점은 studio_amount(45%) / 공연은 두 수수료
vat_deduction_amount, share_amount, withholding_amount,
adjustment_amount (이월 조정 합, 부호 있음), shortfall_amount,
net_amount, item_count, status('pending'|'paid'), paid_at, memo, created_at, updated_at
```
`partner_payout_adjustments` — 정산 뒤에 생긴 돈의 변화를 다음 정산에 싣는다.
```
id, kind, payee_key(=subject의 수취인 키), amount(부호 있음), reason('late_refund'|'showtime_cancel_fee'|'manual'),
source_ref(주문번호/회차 id), memo, created_at, applied_payout_id (정산 기록 때 채움, NULL = 아직 안 실림)
```
- 기록은 **불변 스냅샷**이다(요율이 바뀌어도 이체 근거가 안 변한다). 이체 전(`pending`)에 한해 "기록 취소(다시 기록)"를 허용한다 — 아티스트 후원 정산에 이미 넣은 규칙과 같다. 취소하면 그 정산에 실렸던 조정은 다시 `applied_payout_id = NULL`로 돌아간다.
- 정산 뒤 환불은 **조정 행을 자동으로 만든다**(상점: 이미 정산된 달의 주문이 환불되는 순간 `late_refund`, 환불액×(아티스트 몫 비율)을 음수로). 만드는 자리는 기존 환불 처리 경로 끝(주문이 속한 정산이 `paid`/`pending`인지 보고).
- 조정이 정산금을 넘으면 정산금은 0원으로 두고 남은 음수는 **다음 정산으로 이월**한다(청구는 운영자 판단).

## 5. 흐름과 화면

```
[미리보기] 기존 표/신규 계산  →  막는 조건 확인  →  [정산 기록] (스냅샷 + 조정 반영)
        →  운영자가 계좌 열람 버튼 → 은행 앱 송금 →  [지급 완료] (+메모: 이체일·실제 금액)
```
- **상점**: `/admin/shop` "아티스트 정산 예정" 표 각 행에 [정산 기록] / [지급 완료] / [기록 취소(이체 전)] / [계좌 보기]. 달 이동은 지금처럼.
- **공연**: `/admin/shows/[id]`에 "정산" 절(펀딩의 `FundingPayoutSection`과 같은 구성): 마지막 회차 종료 전에는 "종료 후 기록 가능", 이후 미리보기·막는 조건·기록·지급 완료.
- **계좌 열람**은 새로 만들지 않는다 — `/api/admin/creators/[creatorId]/payout-account`(복호화, 접속기록 `creator_payout_account_view`)를 쓴다. 값은 props에 싣지 않고 버튼 클릭 때만.
- **대시보드**: 대기열에 "정산 기록 대기(상점 달·공연)"와 "이체 대기(상점·공연)". **점검 메일**: 공연은 마지막 회차 종료 + 영업일 14일(약관 기한)을 넘기면 high(`businessDaysAfter`로 펀딩과 같은 방식). 상점은 시기를 약관이 정하지 않아 기한 알림 없이 카드로만.

## 6. 기록을 막는 조건 (펀딩과 같은 틀)

- 계좌 미등록 / 세금 구분 미등록 → 막음. 원천징수면 주민등록번호 보관 여부는 **막지 않고 경고**(번호는 지급명세서 때 필요하지 송금에는 불필요).
- 사업자인데 사업자 정보 미등록 → 막음. 위탁 약관(상점)·주최자 약관(공연) 미동의 → 막음.
- 같은 (kind, subject, period)에 기록이 이미 있으면 거절(DB unique + `already_recorded`).
- 공연: 마지막 회차가 아직 끝나지 않았으면 거절. 계좌 입금(수동 확인) 환불이 미완료(`refund_account` 접수 후 송금 전)면 경고.

## 7. 개인정보·처리방침 (운영자 확인 2026-10-16: **상점·공연 개설자에게도 적용**)

> **P0 문구 개정 완료(PR 번호는 PR 본문에, 2026-10-16)** — 처리방침 13·14·15·18·19항, 상점 위탁 약관 제7조, 판본 `funding-terms-2026-10-16`·`shop-artist-terms-2026-10-16`. 주최자 약관은 손대지 않았다(해시 불변). 아래 "보존·파기 코드"는 이 PR이 **아니라 P1(표 마이그레이션)과 함께** 한다 — 표가 아직 없어 넓힐 대상이 없다. 새 문장은 "정산을 기록하면 …" 조건형이라 코드 확장 전에 배포돼도 거짓이 되지 않는다.

정산 기록 보관·파기 규칙을 상점·공연 개설자에게도 펀딩 개설자와 똑같이 적용한다. 그 결과 **구현 전에 처리방침·약관·보존 로직을 먼저 고쳐야 한다**(P0). 현재 문구는 펀딩 한정이다.

**처리방침(`data/privacyPolicy.ts`) — 고칠 곳**
1. *수집 항목*(14항 "정산을 기록한 경우 자동 생성 — 그 프로젝트의 모금액, … 펀딩 설계비·제작비 공제액 …"): 펀딩 프로젝트 / 상점 아티스트의 달 / 공연 단위로 일반화한다. 상점·공연에서 늘어나는 항목: 판매액, 배송비(아티스트 직접 발송), 이월 조정액, 차액, 정산 단위(달·공연).
2. *사업자 정보 파기 시점*(같은 14항): "사업자 정산 기록"에 상점·공연 정산이 들어가도록 정의를 넓힌다. "정산이 끝나지 않은 펀딩 프로젝트·심사 중이거나 승인된 공연 등록·상점 아티스트 등록이 있는 동안은 파기하지 않는다"는 지금 문구가 이미 세 갈래를 말하고 있어 유지.
3. *주민등록번호 보존 예외*(14·15항): 지금은 "상점 아티스트로 등록된 개설자도 지우지 않는다 — 상점 판매대금은 정산 기록을 따로 남기지 않아 원천징수한 정산이 있었는지 기록으로 가릴 수 없기 때문"이라고 이유를 적었다. 정산 기록이 생기면 이유가 바뀐다 — 원천징수한 정산 기록(상점·공연 포함)이 있으면 보관. 다만 **기록이 생기기 전 거래분**은 기록으로 가릴 수 없으므로 상점 아티스트 예외는 그대로 두고 문구만 "기록이 없는 기간의 거래 때문"으로 고친다.
4. *법정 보존*(18·보존 항목 열거): 개설자 쪽 정산 기록 항목 열거에 위 새 항목을 더한다. 대금 결제 기록에 해당하는 정산 기록은 거래 기록이라 지우지 못한다는 문장이 상점·공연에도 적용된다는 점을 명시.
5. *접속기록 목록*(19항): 상점·공연 정산 안내 메일(P3)을 만들 때 계좌를 여는 일. 그리고 **이번 주에 늘린 열람 기록이 목록에 아직 없다** — 후원 상세, 상점 주문 상세, 소프트웨어 라이선스 목록, 예약·구독·공연 관리·공연 심사 상세, 개설자 단위 주민등록번호 조회, 개설자 계정 수정(서버 로그). 같은 개정에 함께 넣는다.

**약관**
- 상점 위탁 약관 제7조: "정산 시기와 방법은 스튜디오가 따로 알립니다" → 달 단위 정산, 이월 조정(정산 뒤 환불을 다음 정산에서 뺌 — 이미 있는 문장)과 **음수 이월**, 정산 기록이 남는다는 점을 한 줄씩. 처리방침 4항·위탁 약관 제9조 항목 문자열 대조 테스트가 있으므로 둘을 같이 고친다.
- 주최자 약관 제6·7조: 정산 단위(공연 1건)와 회차 취소 결제 수수료 차감은 **이미 적혀 있다**. 음수 이월이 필요하면 한 줄 추가.
- 판본: 처리방침 → `FUNDING_TERMS_VERSION`(펀딩 동의 증거와 같은 게이트), 약관 → `SHOP_ARTIST_TERMS_VERSION`·`SHOW_ORGANIZER_TERMS_VERSION`. 개정 후 상점·공연 개설자는 다시 동의 화면을 본다(판정이 "현재 판본 행이 있는가"이므로).

**보존·파기 코드 — 같이 넓혀야 하는 곳**
- `hasWithheldPayout`(`lib/funding/creatorProjectWrite.ts:463`)과 그 거울(`lib/funding/businessProfile.ts`), 자동 파기 기준(`lib/funding/retention.ts`), 사업자 정산 기록 판정(`creatorEligibility.ts`)이 `funding_project_payouts`만 본다. `partner_payouts`도 보도록 넓힌다 — 안 그러면 상점·공연으로만 정산받은 개설자의 주민번호·사업자 정보가 처리방침과 달리 일찍 지워지거나 영영 안 지워진다.
- 정산 기록 표는 계정이 남아 있는 동안 보관하고 자동 파기 절차를 두지 않는다(펀딩 정산 기록과 같다).

**열람·기록**
- 정산 기록·화면은 이름·금액만 다룬다. 계좌·주민번호는 기존 열람 경로(접속기록 남음)로만, 새 열람 행동은 필요 없다.
- 정산 알림 메일(P3)은 펀딩 `payoutEmail`과 같은 방식: 계좌는 **마스킹된 값**만 싣는다.
