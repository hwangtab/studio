# 프로듀싱 레슨 운영 시스템 — 설계 (2026-10-21)

> **결정(2026-10-21): 계좌·현금 선불이 카드보다 많다 · 결석은 보강하지 않는다. P0(매출 분리)와 P1(수강 등록·회차)은 구현됐다 — 현재 동작의 정본은 코드(`lib/lessons/`)와 CLAUDE.md "프로듀싱 레슨 관리" 절이다.** **P2(수강 계약)도 구현됐다 — 환불 조항(제9조)만 확정 전 초안이라 발송이 잠겨 있다(CLAUDE.md).** 구현에서 설계와 다른 점: 연락처·이메일은 저장하지 않음(P2에서), 구글 캘린더 연동 없음(자동 등록 충돌), `lesson_events` 표 없음, `paused` 상태 없음(일정 변경·결석으로 처리), 보강 없음(스튜디오 휴강만 끝에 회차 추가).

> 운영자 요청(2026-10-21): "레슨 매출도 있고 계약도 맺어야 하고 관리도 해야 하는데 기능이 전혀 없다." 구현 전 설계다. 결정이 필요한 것은 맨 아래 §9.

## 1. 지금 있는 것과 없는 것

레슨 상품: **월 350,000원(VAT 별도), 주 1회 60분 1:1, 컨트롤 룸, 12주 또는 24주 과정**, 첫 상담 무료. 보컬·악기 레슨은 없다(CLAUDE.md "보컬·악기 레슨은 없다").

| 영역 | 있는 것 | 없는 것 |
|---|---|---|
| 결제 | 카드 **정기결제 구독**(`subscriptions.kind='lesson'`, 빌링키, 청구일, 실패 재시도·정지·재개·환불). 카드는 385,000원(+VAT 10%) | **현금·계좌 입금 레슨**(VAT 없음 350,000원)은 수기 매출뿐 — 어느 수강생의 몇 월 치인지 연결이 없다 |
| 매출 | 구독 결제는 매출에 잡힌다 | 유형이 `구독` 하나라 **연습실 월 구독·아티스트 후원과 섞인다**. 레슨 매출만 볼 수 없다. 현금 레슨은 수기 매출(유형 선택)에만 있다 |
| 계약 | 연습실 임대차(`contracts`), 음원 제작 용역(`production_contracts`) | **수강 계약서가 없다** — 기간·횟수·결석·보강·환불·녹음 자료 이용이 문서로 합의되지 않는다 |
| 관리 | 구독 목록·상세(결제 상태 중심) | **수강생 명부, 시간표, 회차, 출석·보강, 수업 기록·진도, 종료 임박·재등록**이 없다. 컨트롤 룸을 쓰는데 **녹음실 예약과 시간이 겹치는 것을 막는 장치도 없다** |

## 2. 설계 원칙

1. **수강 등록(enrollment)이 중심 단위**다. 한 사람의 한 과정(12주/24주) = 한 행. 계약·구독·시간표·회차·수납이 모두 여기에 달린다.
2. **새 표를 만들고 기존 표에 컬럼을 더하지 않는다**(0022 함정 — 관계 조회가 전체 컬럼을 SELECT). 표가 없는 DB에서는 레슨 화면만 "미적용"으로 열리고 결제·예약은 안 깨진다.
3. **돈의 정본은 기존 장부 그대로**: 카드는 `orders/payments`(구독), 현금은 새 `lesson_payments`. 매출 현황은 두 곳을 합쳐 "레슨" 유형으로 낸다(월 입주 매출처럼 별도 로더).
4. 연락처·이메일은 **암호화 한 칸**(`private_enc`, 월 입주와 같은 방식). 목록·props에 싣지 않고 버튼으로만 열며 열람은 접속기록.
5. 계약 엔진은 **음원 제작 계약을 재사용**한다(템플릿 사본·조건부 서명·지문·PDF·연락처 뒷자리·법정대리인). 새 엔진을 만들지 않는다.
6. 구글 캘린더는 DB의 투영이다(월 입주와 같은 규칙) — 정본은 DB.

## 3. 데이터 모델 (새 표, 마이그레이션 0081~)

```
lesson_enrollments            -- 수강 등록
  id, status(inquiry|contract_pending|active|paused|completed|ended|cancelled)
  course_weeks (12|24), start_date, end_date(예정), weekday(0-6), start_time(HH:MM, KST), duration_min(60)
  monthly_amount(공급가), pay_method('card_subscription'|'bank'|'cash'), subscription_id(null이면 카드 아님)
  contract_id(수강 계약), student_private_enc(이름 제외 연락처·이메일·미성년 여부 JSON), student_name,
  guardian_*(미성년이면 production_contract_signers 방식), curriculum_stage, note, created_at, ended_on, ended_reason
lesson_sessions               -- 회차 (수업 한 번)
  id, enrollment_id, seq, scheduled_at, status(scheduled|done|student_absent|makeup_pending|makeup_done|studio_cancelled)
  makeup_of(session id), gcal_event_id, block_id(예약 불가 블록), note_enc?(수업 기록 — 개인정보 없음이면 평문), homework, topic
lesson_payments               -- 현금·계좌 수납
  id, enrollment_id, paid_on, amount, vat_amount, period_label('2026-10'), method, memo, receipt_issued(현금영수증/계산서 발행 여부)
lesson_events                 -- 변경 이력(추가만): 일정 변경·보강·정지·재개·종료 — contract_admin_events 방식(개인정보 없음)
```

- 회차는 등록 때 **과정 길이만큼 미리 만든다**(12주면 12행, 월 4회 × 3). 보강은 새 행(`makeup_of`)으로.
- 카드 구독의 청구일·정지·환불은 **기존 구독 코드가 그대로** 맡고, 등록은 `subscription_id`로 가리킨다(구독을 정본으로 두고 복사하지 않는다).

## 4. 계약 (수강 계약서)

`lib/contracts/lesson/` — 음원 제작 용역 계약의 엔진을 재사용하고 템플릿·terms만 다르다(`kind: 'lesson-12' | 'lesson-24'`). 설계 문서의 조항 초안:

1. 목적·과정(12/24주, 주 1회 60분, 커리큘럼 단계) · 수업 장소·시간(고정 요일·시각)
2. 수강료(월 350,000원 VAT 별도 — 카드 385,000원, 현금·계좌 350,000원)·납부 방식·납부일·연체
3. **결석·보강**: 수강생 사정 결석(예: 24시간 전 통지 시 월 1회 보강, 그 외 소멸), 스튜디오 사정 휴강은 전액 보강
4. **중도 해지·환불**(§9 확인 필요 — 숫자는 법적 기준 확인 뒤 확정)
5. 수업 중 녹음·결과물의 **이용 범위**(수강생 작품 저작권은 수강생, 수업 시연 자료는 스튜디오) · 스튜디오 **장비 사용·파손**
6. 개인정보(처리방침 연결, 보관 기간) · 미성년자(법정대리인 서명, 연습실과 같은 방식) · 분쟁 해결(민사소송법 관할)

체결 흐름은 제작 계약과 같다: 운영자가 등록에서 "계약 보내기" → 수강생 링크(`/ko/contracts/lesson/[id]/sign`, 비공개 경로 4곳 규칙 그대로) → 서명 → 성립하면 등록이 `contract_pending → active`로 넘어가고 **첫 수업 전까지 카드 등록 안내**(카드면)가 간다.

## 5. 관리 화면 (관리자 `/admin/lessons`, 메뉴는 "녹음실" 묶음)

- **목록**: 수강 중·정지·종료 임박(마지막 회차 2주 안)·계약 대기·결제 문제 필터. 카드는 "이번 주 수업"(요일 순)이 첫 줄.
- **상세(수강생 한 명)**: 상태·과정·고정 시간 / 회차 표(날짜·상태·보강 연결·메모) / 커리큘럼 진도 단계 / 결제(카드면 구독 상태 링크, 현금이면 수납 기록 + "수납 기록" 버튼) / 계약 / 이력.
- **회차 조작**: 완료 · 수강생 결석(보강 가능 여부 판정) · 스튜디오 휴강 · **일정 변경**(캘린더·예약 불가 블록 함께) · 수업 기록(다룬 내용·과제).
- **대시보드 큐**: 오늘 수업 / 완료·결석 표시 대기(지난 수업) / 종료 임박 / 계약 서명 대기 / 연체(현금 납부일 지남) — 기존 "처리할 일"에 같은 방식으로.
- **컨트롤 룸 충돌 방지**: 고정 시간을 정할 때 녹음실 예약·다른 수강생 시간과 겹치면 막는다. 확정 회차마다 **"예약 불가 블록"**(결제 링크의 `availability_blocks` 방식)을 만들어 웹 예약이 그 시간을 못 잡게 하고, 구글 캘린더에는 투명 일정으로 올린다(월 입주와 달리 이 시간은 실제로 방을 점유하므로 **바쁨**으로 올린다).

## 6. 매출

- 매출 유형 `lesson`("프로듀싱 레슨") 신설, 직접 서비스. 소스 둘을 한 로더(`lib/ops/lessonRevenue.ts`)가 합친다:
  ① 카드 구독 결제 — `subscription_id`가 레슨 등록에 연결된 구독의 `orders`(지금은 `구독`으로 섞여 나가는 것을 **레슨 구독만** 이 유형으로 옮기고 연습실·아티스트 구독은 그대로).
  ② 현금·계좌 `lesson_payments` — 수납일 기준.
- **VAT**: 카드 = 350,000 + 35,000 = 385,000원(부가세 35,000원 분리, 기존 구독 규칙). 현금은 부가세를 받지 않으므로 350,000원·부가세 0(기존 안내와 같다). `lesson_payments.vat_amount`에 그대로 적는다 — 세무 구분의 근거.
- 환불·중도 해지 정산은 카드는 기존 구독 환불, 현금은 `lesson_payments`에 음수 행(사유 필수)으로.
- 수강생별 누적 수납·미수금(예정 대비), 월별 레슨 매출·신규·종료·재등록률은 매출 현황의 "레슨" 칸에 요약만(상세는 `/admin/lessons`).

## 7. 알림

이메일만(문자 인프라 없음): 계약 발송·서명 완료 / 수업 전날 리마인드(수강생) / 일정 변경·휴강 / 종료 2주 전 재등록 안내 / 카드 미등록·결제 실패(기존 구독 메일 그대로). 운영자 메일은 기존 운영 점검 메일에 "오늘 수업·종료 임박·연체"를 얹는다.

## 8. 단계

| 단계 | 내용 | 마이그레이션 | 크기 |
|---|---|---|---|
| **P0 매출 분리** | 레슨 구독을 `lesson` 유형으로 분리, 현금 레슨을 수기 매출이 아니라 `lesson_payments`로(등록 없이 수강생 이름·월만 적는 간이 입력) | 0081 `lesson_payments` | 작음 — 먼저 |
| **P1 수강 등록·시간표·회차** | `/admin/lessons`, 등록 생성(과정·요일·시간), 회차 자동 생성, 충돌 방지·예약 불가 블록·캘린더, 완료·결석·보강·휴강, 수업 기록 | 0082 `lesson_enrollments`·`lesson_sessions`·`lesson_events` | 큼 |
| **P2 수강 계약** | 템플릿 2종, 전자서명(제작 계약 엔진 재사용), 성립 → 수강 시작, 법정대리인 | (제작 계약 표 재사용 또는 0083) | 중간 |
| **P3 알림·재등록** | 리마인드·종료 임박·재등록 안내, 대시보드 큐, 운영 점검 메일 | 없음 | 작음 |
| **P4 수강생 화면** | 관리 링크로 일정 확인·결석 신청(보강 요청) | 없음(토큰 해시 컬럼은 P1에 포함) | 선택 |

P0만으로도 "레슨 매출을 따로 본다"는 요구는 풀린다. P1~P2가 계약·관리의 본체다.

## 9. 결정이 필요한 것 (운영자)

1. **결제 방식** — 모든 수강생이 월 정기결제(카드)인가, 현금·계좌 선불이 섞이는가? 12/24주를 **월 단위로 청구**하는 지금 구조 그대로 둘까, 과정 일괄 선불도 받을까?
2. **결석·보강 규칙** — 수강생 사정 결석은 몇 시간 전 통지에 월 몇 회까지 보강? 스튜디오 사정 휴강은 전액 보강으로 해도 되나?
3. **중도 해지·환불 숫자** — 교습소·학원 성격의 레슨은 교습비 반환 기준(교육 관련 법령)이 따로 있을 수 있다. **적용 여부와 신고 의무를 법률 확인한 뒤** 계약서 숫자를 정한다(확인 전에는 숫자를 못 박지 않는다). 이 확인이 P2의 선행 조건이다.
4. **수업 녹음·결과물** — 수강생 작품 저작권, 수업 시연 자료의 스튜디오 이용 범위를 어디까지 쓸지(후기·홍보 사용 동의 포함).
5. **현금 레슨의 증빙** — 현금영수증·세금계산서를 발행하는가? 발행하면 `lesson_payments.receipt_issued`와 매출 부가세 구분이 필요하다.
6. **수강생 규모와 강사** — 동시 수강 인원 상한, 강사가 항상 본인 한 명인지(여러 명이면 강사 칸을 P1에 넣는다).
7. **미성년 수강생**을 받는가(받으면 법정대리인 서명을 P2에 포함, 아니면 연습실처럼 만 19세 미만을 막는다).
8. **첫 상담 무료** 기록 — 상담(inquiry) 단계를 등록에 남길지(전환율 보려면 필요).
