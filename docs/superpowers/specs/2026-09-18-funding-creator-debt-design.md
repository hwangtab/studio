# 펀딩 셀프 개설 4차 — 3차가 남긴 빚

작성 2026-09-18. 3차(PR #188, `56c0cc0e7f`)가 머지된 직후의 설계다.

3차는 개설자가 연 프로젝트를 운영자가 심사해 공개하는 경로를 닫았다. 그 과정에서 네 가지가
남았다. 하나는 3차가 **새로 만든 결함**이고, 둘은 오픈 전에 반드시 막아야 하는 것이며,
나머지 하나는 3차가 스스로 "다음에 정한다"고 적어 둔 결정이다.

이번 계획은 새 기능을 만들지 않는다. 정산·개설자 통계·배송지 전달은 5차로 넘긴다.

## 1. 왜 지금인가

| 항목 | 지금 무슨 일이 나는가 |
|---|---|
| 개설자 이름 기본값 | 공개 페이지에 이메일 로컬파트가 뜨고, 승인되면 본인도 못 고친다 |
| 매직링크 전역 캡 | 주소·IP를 흩뿌리면 발송량에 천장이 없다 |
| 승인 뒤 수정 경로 | 오탈자 하나를 고칠 방법이 개설자에게도 운영자에게도 없다 |
| 내부 메모 칸 | 운영자가 내부 기록이라 믿고 적은 문장이 개설자에게 즉시 보인다 |

## 2. 결정된 것 (이 설계의 전제)

- **플랫폼 수수료율은 5.5%(부가세 포함)** — 텀블벅 기준. 이번 범위에는 정산이 없으므로
  **코드에 넣지 않는다.** 5차에서 상수로 박고 개설자 약관 제6조를 채운다. 여기 적어 두는
  이유는 그때 이 값을 다시 묻지 않기 위해서다.
- **승인 뒤 본문은 개설자가 바로 고친다.** 재심사 대기열을 만들지 않는다 — 오탈자 하나에
  심사를 기다리게 하는 것이 더 나쁘다. 대신 고칠 때마다 운영자에게 알린다.
- **리워드는 설명글까지 통째로 잠근다.** 후원자가 보고 결제한 약속이라, "CD 1장 + 포스터"가
  후원 뒤에 "CD 1장"이 되면 후원자 약관 제8조의 "표시·광고와 다르게 이행"에 걸리고 판매자인
  스튜디오가 3개월짜리 청약철회를 받는다.

## 3. 개설자 이름 기본값

### 지금

`lib/funding/creatorToken.ts:45`가 가입 시 `name: normalized.split('@')[0]`을 넣는다.
이름을 **채워 버리므로** 미설정과 설정을 구분할 수 없고, `findMissingRequiredSections`의
`creatorName` 검사(빈 문자열만 본다)는 영영 발동하지 않는다.

3차가 그 이름을 공개 상세의 판매자 표시 옆에 그리기 시작했고(`ProjectDetailView`),
동시에 승인된 프로젝트가 있으면 이름을 잠갔다(`saveCreatorSection`). 둘이 겹쳐서:

> 프로필을 한 번도 안 건드린 개설자가 승인되면 공개 페이지에 "개설자 hwangtab · 판매자
> 스튜디오 놀"이 뜨고, 그 뒤로는 본인도 운영자도 못 고친다.

### 고치는 방법

`lib/funding/creatorValidation.ts`에 판정 하나를 둔다.

```ts
/** 가입 시 채워 넣는 이메일 로컬파트는 "개설자가 고른 이름"이 아니다. */
export const isDefaultCreatorName = (name: string, email: string): boolean =>
  name.trim() === email.split('@')[0];
```

세 곳이 이것을 본다.

1. **`findMissingRequiredSections`** — `creatorEmail`을 함께 받아 기본값이면 "개설자
   정보(이름)"를 미비 목록에 넣는다. 심사 신청(`submit.ts`)과 승인(`decideProject`)이 같은
   함수를 쓰므로 두 관문이 한 번에 닫힌다.
2. **이름 잠금의 예외**(`saveCreatorSection`) — 지금 이름이 기본값이면 잠그지 않는다.
   설정한 적 없는 값을 잠그는 것은 잠금이 아니라 사고다. **이미 로컬파트 이름으로 남아 있는
   기존 행도 이 예외로 스스로 풀린다 — DB를 손댈 필요가 없다.**
3. **개설자 편집 화면** — 이름이 기본값이면 심사 신청 자리에 무엇이 비었는지 보여 준다.
   지금도 미비 항목을 보여 주는 자리가 있으므로 새 화면을 만들지 않는다.

### 가입 시 이름을 아예 비우지 않는 이유

기존 행이 이미 로컬파트를 갖고 있다. 새로 비우면 "빈 이름"과 "로컬파트 이름" **두 가지
미설정 상태**가 생기고, 그때부터 모든 검사가 두 경우를 다 봐야 한다. 판정을 한 군데
(`isDefaultCreatorName`)에 모으는 편이 낫다.

## 4. 매직링크 전역 일일 캡

### 지금

`pages/api/funding/creator/login.ts`는 IP별(`creator_login:ip:*`)과 주소별
(`emailRateLimitKey`) 제한을 건다. 둘 다 **키가 요청자마다 다르므로**, 주소와 IP를 흩뿌리면
발송량에 천장이 없다. 메일 청구서와 발신 도메인 평판이 걸려 있다.

### 고치는 방법

`consumeRateLimit(key, limit, windowSeconds)`는 이미 `rate_limits` 테이블의 원자적 UPSERT라
서버리스 다중 인스턴스에서도 공유 카운터로 동작한다. 고정 키 하나를 더한다 —
`creator_login:global`, 창 86400초.

두 가지가 설계의 핵심이다.

**캡은 메일을 실제로 보내기 직전에만 소비한다.** 주소별 제한에 걸려 이미 돌아가는 요청이
전역 예산을 태우면, 한 주소를 두드리는 것만으로 전체를 잠글 수 있다. 호출 순서는
IP → 주소 → **전역** → 발송이다.

**캡이 걸리면 운영자에게 알린다.** 캡에 걸린 정상 사용자는 메일을 못 받는데 화면은 성공이라고
답한다(주소 존재 여부를 숨기려면 그래야 한다 — 기존 주석에 그 이유가 적혀 있다). 운영자가
모르면 **아무도 모른다.** 알림 메일은 별도 레이트리밋 키(`creator_login:global_alert`)로
창당 한 번만 보낸다. 캡에 걸린 상태에서 알림이 쏟아지면 그것이 두 번째 사고다.

한도 값은 상수로 두고 주석에 근거를 적는다. 개설자 수가 두 자리인 동안은 하루 수십 통이
정상 상한이다.

## 5. 승인 뒤 수정 경로

### 지금

`lib/funding/creatorProjectWrite.ts`의 `guard`가 `canCreatorEdit(reviewStatus)` 불리언
하나로 네 구획(기본정보·스토리·리워드·개설자)을 통째로 열고 닫는다. `approved`는 닫힘이므로
승인 뒤에는 개설자가 아무것도 못 고친다. 운영자에게도 경로가 없다 — 관리자 API의 액션은
`approve`·`request_changes`·`reject`·`archive`·`set_review_note`뿐이다.

그런데 개설자 화면은 `components/funding/creator/types.ts`에서 "내용을 고치려면 운영자에게
문의해 주세요"라고 안내한다. **가리키는 곳이 없는 안내다.**

### 구획별 규칙으로 바꾼다

전이표가 있는 `lib/funding/reviewTransition.ts`에 표를 하나 더 둔다. 조건문을 흩지 않는다 —
3차가 전이표로 얻은 이득(전수 조합 테스트가 빠진 조합을 잡는다)을 그대로 쓴다.

| 상태 | 열리는 구획 |
|---|---|
| `draft` · `changes_requested` | 기본정보 · 스토리 · 리워드 · 개설자 |
| `approved` | 스토리 · 기본정보(일부) |
| `submitted` · `rejected` | 없음 |

개설자 구획(계정 프로필)은 프로젝트가 아니라 계정 소속이라 이 표를 타지 않는다(3차 결정).
이름 잠금은 §3의 규칙이 따로 본다.

### 기본정보는 필드 단위로 연다

`BasicSection`은 `title`·`summary`·`slug`·`goalAmount`·`startAt`·`endAt`·`coverUrl`이 한
덩어리라 구획째 열 수 없다. 리워드의 `lockedViolation`과 **같은 꼴로** 필드 단위 가드를 둔다.

| 필드 | 승인 뒤 | 왜 |
|---|---|---|
| `slug` | 잠김 | 바뀌면 후원자가 manage 페이지에서 프로젝트를 못 찾는다 |
| `goalAmount` | 잠김 | 공개된 달성률의 분모다 |
| `startAt`·`endAt` | 잠김 | 모금 기간은 후원자와의 약속이다 |
| `title` | 열림 | 오탈자를 고칠 수 있어야 한다 |
| `summary` | 열림 | 같은 이유 |
| `coverUrl` | 열림 | 잘못 올라간 표지가 영영 남는 것을 막는다 |

리워드 구획은 승인 뒤 통째로 잠긴다 — 설명글까지(§2).

### 수정됐다는 사실은 새 컬럼 없이 안다

`updatedAt > approvedAt`이면 승인 뒤에 고친 것이다. 두 컬럼 모두 이미 있다.

- **심사 화면**이 그 표시를 단다("승인 뒤 N회 수정" 같은 횟수는 셀 수 없으므로 "승인 뒤
  수정됨"과 마지막 수정 시각만 보여 준다).
- **운영자에게 메일이 간다.** 판정 메일과 같은 모듈(`lib/funding/reviewEmail.ts`)에
  문면을 더한다. 매 저장마다 보내면 메일이 쏟아지므로 `consumeRateLimit`으로 프로젝트별
  창을 둔다 — **창 안의 나머지 저장은 메일을 보내지 않는다**(합쳐서 보내는 것이 아니라
  억제한다). 운영자가 놓치지 않는 것은 메일이 아니라 심사 화면의 "승인 뒤 수정됨" 표시다.
  메일은 그 화면을 보러 가라는 신호일 뿐이므로 억제해도 정보가 사라지지 않는다.

## 6. 내부 메모 칸 분리

### 지금

`funding_projects.review_note` 한 칸을 네 가지가 공유한다 — 보완 요청 사유, 반려 사유,
보관 사유, `set_review_note`. **전부 개설자 화면 두 곳에 그대로 렌더된다**
(`creator/[id].tsx:122`, `creator/index.tsx:81`). 운영자가 내부 기록을 남길 칸이 없다.

### 고치는 방법

`funding_projects.internal_note` 컬럼을 더한다. **이번 계획의 유일한 마이그레이션**이다 —
`npm run db:generate`로 SQL을 생성·커밋하고 **적용은 운영자가 직접 한다**(`db:migrate`를
실행하지 않는다).

- 관리자 API에 `set_internal_note` 액션. `set_review_note`와 같은 모양이고 같은 낙관적
  잠금을 탄다.
- **`AdminProjectDetail`에 싣되 개설자 쪽에는 어떤 경로로도 싣지 않는다.** 3차가 정산
  필드에 쓴 화이트리스트 테스트와 같은 방식으로, 개설자 화면 props에 `internalNote`가
  없다는 것을 테스트로 고정한다.
- 심사 화면은 두 칸을 **서로 다른 색·다른 라벨**로 나눠 그린다. 라벨은 사실대로 적는다 —
  "개설자에게 보이는 메모" / "내부 기록 — 개설자에게 보이지 않습니다".

### 이걸로 풀리지 않는 것

보관과 반려는 여전히 DB에서 같은 `rejected`다. 내부 메모가 생기면 운영자가 구분을 적어 둘
수 있지만, **자동으로 구분되지는 않는다.** `reviewStatus`에 값을 더하는 것은 이번에도 하지
않는다 — 그러면 전이표·화면 라벨·통계가 전부 따라 움직여야 하고, 그건 이 계획의 목적
(빚 갚기)이 아니다.

## 7. 공개 화면에 생기는 변화

**없다.** 네 항목 모두 개설자·운영자 화면과 서버 규칙만 건드린다. 공개 상세에 뜨는 개설자
이름이 로컬파트에서 실명으로 바뀌는 것이 유일한 눈에 보이는 차이인데, 그건 개설자가 이름을
채운 결과지 이 코드가 화면을 바꾼 것이 아니다.

진행 중인 마크다운 프로젝트(`keep-singing-for-palestine`)는 `creator`가 `null`이라 어느
항목도 닿지 않는다. 빌드 산출물로 확인한다.

## 8. 검증

```
npm run type-check
npm run lint
npm test
env -u TURSO_DATABASE_URL -u TURSO_AUTH_TOKEN npm run build
```

`pages/`·`components/` 아래를 건드린 작업은 **빌드까지 돌려야 한다** — 타입 검사와 테스트를
통과하고 빌드만 잡는 클라이언트 번들 파손이 이 저장소에서 실제로 났다(CLAUDE.md).

전이표를 바꾸므로 전수 조합 테스트가 새 구획 규칙까지 덮어야 한다 — 상태 × 구획 전부.

## 9. 이번 범위에서 하지 않는 것

- 정산 계산·관리자 정산 탭·개설자 약관 제6조 채우기 (5차, 수수료율 5.5%는 정해져 있다)
- 개설자 통계 화면
- 배송지를 개설자에게 넘기는 경로와 그에 따른 처리방침 개정 — 지금 약관이 "발송은 스튜디오가
  처리한다"로 정합하게 좁혀져 있으므로 빚이 아니라 이월이다
- 고아 blob 정리, 리워드 순서 변경
- `reviewStatus`에 보관 전용 값 추가

## 10. 구현 순서

1. 개설자 이름 기본값 — `isDefaultCreatorName`과 세 소비처
2. 매직링크 전역 캡 — 호출 순서와 운영자 알림
3. 내부 메모 — 마이그레이션 생성, API 액션, 심사 화면 두 칸, 누수 테스트
4. 승인 뒤 수정 경로 — 구획별 표, 기본정보 필드 가드, 수정 알림
5. 전체 검증과 문서(CLAUDE.md·이 스펙 갱신)

3이 4보다 앞인 이유: 4가 심사 화면을 건드리는데, 3이 그 화면에 칸을 하나 더한다. 순서를
뒤집으면 같은 파일을 두 번 고친다.
